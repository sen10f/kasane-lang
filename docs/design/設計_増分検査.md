# 設計メモ: `ksn check` の増分化（第 1 段・第 2 段）

対象: docs/plan/実装計画.md 4 章 段階 4 の 3、2.4 の最後の段落。実装は `stage0/src/check_cache.rs` と `cli.rs` の `full_check`。

## 1. 結論（第 1 段でやったこと）

> 第 2 段で保存の単位をファイルから定義にした。4 章のファイル単位の保存（`FileCheck`・文面のキー）は 8 章の定義単位に置き換わっている。4 章は第 1 段の記録として残す。

- 意味の検査（`check.rs` / `types.rs` / `borrowck.rs`）は、定義単位で閉じてキーで決まる段が**ほとんどない**（3 章）。第 1 段では保存しない。毎回やり直す（過剰無効化は許容、過小無効化は不可）。
- 時間を測ると（4 章）、`ksn check` の支配項は意味の検査ではなかった。(a) ファイル 1 本の文面だけで決まる検査（正規形の判定・lint・文法。`full_check` の前半）と、(b) `check_recursion` の頂点ごとの到達集合（関数数の 2 乗）。
- (a) は**ファイル単位**で保存する（既定で有効。`KSN_CHECK_CACHE=0` で無効）。(b) はキャッシュではなくアルゴリズムの修正（Tarjan 法、結果は同じ）。こちらは常に有効。
- 定義単位のキー（定義の正規形 + 依存先の外部面ハッシュ）は、2 章で設計し、実装は意味の検査を定義単位に切り出せた段から入れる（第 2 段）。

## 2. キーの設計（定義単位。第 2 段の仕様）

保存の単位は定義（`fn` / `type` / `enum` / `trait` / `impl` / `const` / `static` / `test`）ごとの診断の列。

```
K(def) = H(ksn 実行体の中身 ‖ edition ‖ 検査の設定 ‖ 定義の正規形 ‖ 解決環境 ‖ 依存先の外部面)
```

- 検査の設定: （`KSN_STRICT_TYPES` と `--no-strict-types` は 2026-11-24 に廃止し、E2044 は常に有効なので入れない）、`[unsafe] modules`、統合テストのファイル集合、`KSN_TYPE_COVERAGE` など診断に影響しうる環境と設定をすべて入れる。入れ忘れると過小無効化になる。
- 定義の正規形: `fmt` を通した定義のテキスト。行番号は診断に入るので、**診断の位置を持つ限り行番号もキーに入れる**（入れない場合は位置を相対化して保存し、復元時に足す）。
- 解決環境: その定義があるファイルの `import` 行（名前の解決が変わる）。
- 依存先の外部面: 定義が参照する定義の宣言（ヘッダ。型・`uses` / `panics` / `stack` / `pub` / `impls` / ジェネリクスの境界・トレイトの全メソッドシグネチャ・型のフィールドと派生）のハッシュ。

何がキーに入らないと過小無効化になるか（他の定義の**本体**に依存する箇所）:

| 箇所 | 依存 | キーへの入れ方 |
| --- | --- | --- |
| 効果の推論（非 pub の `fn` は `uses` / `panics` を省略でき、呼び出し先から推論する。`infer.rs`） | 呼び出し先の推論結果 = 呼び出し先の本体 | 呼び出し先の**推論後**の効果をキーに入れる（宣言でなく結果）。推移的なので、推論結果ごと SCC 単位でハッシュする |
| 再帰・`stack` の見積り（`check_recursion` の `go`、E4010〜E4012） | 呼び出しグラフ全体とフレームの大きさ | 到達する定義の本体（グラフの推移閉包）を入れるか、保存しない。第 1 段は保存しない |
| 型推論（`types.rs`）のクロージャの効果・`Fn` 境界の推論 | 渡したクロージャ自身の本体 | 同じ定義の内側なので本体のハッシュで足りる。ただし推論は呼び出し先の**宣言**の型だけを使うこと（本体は見ない）を保つ必要がある。ジェネリクスの具体化はキーに型引数を入れる |
| 借用の省略規則（`check_elision` と `borrowck.rs`） | 呼び出し先のヘッダ（戻り値のライフタイムの結び方） | 外部面に含まれる |
| `tc_fn` の move / 線形の追跡、`let_tys`・`tytab` | `TypeCk` の全定義分の型表（`self.mv_types = tk.tytab`）。定義間で共有される状態 | 診断だけでなく型表も保存しない限り、段を飛ばせない |
| 派生・`impl` の整合（`check_impls` / `check_derive`） | 型の全フィールドと全 `impl` | `impl` / `trait` の集合のハッシュをキーに入れる（保守的） |
| 公開性（`check_visibility*`）・層の向き | 参照先の定義の場所と `pub` | 外部面に含まれる |

## 3. 各段をコードで読んだ判断

`Checker::run` の段のうち、定義単位に閉じてキーで決まるもの・決まらないもの:

| 段 | 判断 | 理由 |
| --- | --- | --- |
| `check_elision`（E3020 / E3021） | 閉じている（ヘッダだけ）。ただし費用がほぼ 0 | 他の定義を見ない。保存する価値がない |
| `check_header_types` / `check_dotted_types` / `check_generic_bounds` | 閉じていない | `self.p.types`（全プログラムの型の集合）に依存。環境の外部面が要る |
| `TypeCk::check_def`（型推論） | 閉じていない | 診断のほかに `let_tys` / `tytab` / `recv_log` / `edges` / `eff_checks` / `closure_asts` を共有の表へ出し、後段（`tc_fn`、`check_recursion`、E2042、E3002）が読む。診断だけを保存すると後段が壊れる |
| `tc_fn`（move・線形） | 閉じていない | 上の型表を読む |
| `check_recursion`（E4010〜E4012） | グラフ全体 | 3 章の表のとおり |
| `check_impls` / `check_derive` / `check_linear*` / `check_visibility` | 全体 | 型・`impl` の集合に依存 |
| **ファイルの文面検査**（正規形・lint・文法） | **ファイルの文面とパスだけで決まる** | `format_source` / `Lint` / `Grammar::check` は文面と `path` / `relpath` しか読まない（`fmt.rs`・`lint.rs`・`grammar.rs` に環境変数・ファイル読み・グローバル状態がないことを確認した）。他のファイル・標準ライブラリ・依存に依存しない |

意味の検査の費用は小さい（3000 関数で `TypeCk` 0.2〜0.8 秒、`tc_fn` 0.1〜0.9 秒）。定義単位の保存に必要な「型表の保存と復元」は大きい作業で、利得は小さい。まず文面検査と `check_recursion` を直した。

## 4. 実装した範囲（第 1 段）

### 保存するもの

ファイル 1 本について `FileCheck { grammar: (一致か, メッセージ, 行), skip: bool, lint: [(コード, 行, メッセージ)] }`。

- `skip` は「`ksn fmt` で直せるので lint を報告しない」の判定（`full_check` の従来の `continue`）。
- 致命かどうか（`run_mode` の `unused`、`order`）は保存せず、読み出し後に毎回決める（呼び出しの種類に依存するため）。
- 構文エラーのファイル（`s.error`）、CR・タブ・行末の空白・末尾の改行の検査、`rustisms` は毎回やる（費用が小さい、または保存の対象外）。

### キー

`K = H(ksn の識別子 ‖ ソースのパス ‖ lint 用の相対パス ‖ ソースの文面)`。各部分は長さを前置して連結する。ksn の識別子は 9 章の `KSN_BUILD_ID`（版・検査の実装が変われば変わる）。edition・`KSN_STRICT_TYPES` などは、この段の結果が依存しないのでキーに入れない（意味の検査を保存するときに入れる。2 章）。

### 置き場所と形式

`<KSN_CACHE_DIR>/check/<KSN_BUILD_ID の先頭 16 桁>-<H(パス ‖ 相対パス) の先頭 32 桁>.json`（8 章で接頭辞を足した）。掃除の記録は `check/.stat.json`。1 ファイル 1 スロットで、内容が変われば上書きする。中身は `{"key", "sum", "data"}`。`sum` は `data` の SHA-256。書き込みは同じ置き場の一時ファイル (`<スロット>.tmp<pid>-<連番>`) へ書いて `rename`。`cli.rs` の `evict`（ビルドキャッシュの上限）はこのディレクトリを対象にしない。

### 上限と削除（第 1 段で既定を有効にするための条件）

- 上限は**ビルドキャッシュとは別の予算**にした。`KSN_CHECK_CACHE_MAX`（バイト、ブロック単位）、既定 64 MiB（`check_cache::DEFAULT_MAX`）。件数の上限 `KSN_CHECK_CACHE_ENTRIES`、既定 8192。`KSN_CACHE_MAX`（既定 2 GiB）は共有しない。理由: 検査のスロットは 1 本数 KB で、ビルドの上限を小さくしたときに検査の置き場が毎回空になるのを避けるため。
- 削除は `check_cache::trim`。`full_check` の終わりに**1 回だけ**呼ぶ。全体を数え直すのは記録が無いとき・見積もりが上限を超えたとき・最後に数えてから 1 時間たったときだけ（8 章）。
- LRU にするため、命中するたびにスロットの更新時刻を進める (`touch`)。

## 8. 置き場の掃除（2026-11-13 の改修）

第 1 段の掃除は、毎回 `read_dir` と `metadata` で置き場の全ファイルを数えていた。また大きさを中身のバイト数で数えていたので、4 KiB のブロックを占めるファイルの実際の量を 4 倍以上過小に見ていた（66,457 件・`du` で 265 MB の置き場が、上限 64 MiB の中にあるとみなされた）。以下で直した。

- **大きさはブロック単位**で数える（`disk_size`: 各ファイルを 4 KiB に切り上げる）。上限を超えたら使用量（同じ数え方）が上限以下になるまで消す。
- **件数の上限**（既定 8192）を別に設けた。使用量の上限だけでは 1 本 4 KiB の最小単位で 1 万数千件まで許すため。
- **記録 `.stat.json`**（置き場の中、`.` で始まるので数えない）に、見積もりの大きさ・件数・最後に数えた時刻を持つ。`store` / `load` はプロセス内で増分を `PEND_*` にためて、`trim` が記録へまとめて足す（書き込みのたびに記録を読み書きしない）。
- **数え直すのは**記録が無い・壊れている、見積もりが上限を超えた、最後に数えてから 1 時間たった、のどれかのときだけ。それ以外は記録を読んで増分を足すだけ。数え直しで上限を超えていたら、上限の 8 分の 1 下まで消す（毎回の実行で消さないため）。
- **古い実行体のエントリを先に消す**。スロット名を `<KSN_BUILD_ID の先頭 16 桁>-<パスの hash>.json` にした。接頭辞が今の実行体と違うもの（と接頭辞の無い古い形式のもの）を先に、次に更新時刻の古いものから消す。鍵には識別子が入るので、古い実行体のエントリが当たることはない。
- 記録の見積もりは、同時に走るプロセスの書き込みで多少ずれる（読み書きを排他しない）。ずれは 1 時間ごとの数え直しで直り、結果（診断）には影響しない。記録は一時ファイルから `rename` で置く。

### 計測（2026-11-13、Linux、VM の Xeon E5-2620 v4）

- 数え方の費用: 66,457 件の置き場を全部数える（`scan`、旧 `trim` が毎回やっていた費用）は約 220 ms。記録だけを見る経路（数え直さない場合）は約 34 μs（`bench_trim_66k_entries`、`cargo test --release --bin ksn bench_trim_66k -- --ignored --nocapture`）。
- `ksn check`（`examples/demo`、ウォームの置き場、3 回の中央付近）: 旧 ksn は 66,457 件の置き場で約 1.0 秒（毎回 66,457 件を数える）。新 ksn は初回だけ上限に合わせて 7,169 件（記録を含む）に減らす（約 1.7 秒）。その後は約 0.35 秒。キャッシュ無効（`KSN_CHECK_CACHE=0`）は約 0.14 秒。
- 空の置き場では新 ksn も約 0.35〜0.45 秒で、残りの固定費は置き場の大きさに依らない（実行体のハッシュなど。原因は未調査 → 9 章で解決）。
- 並行の `ksn`（テストの並列実行、LSP）が同じ置き場を使っても壊れない: 読む側は完全なファイルだけを見る（`rename`）。消えたファイルは未命中になるだけで、診断は変わらない。`trim` が他のプロセスの書いた直後のものを消しても、結果は変わらず再計算するだけ。

### 破損・不一致

読み込みで、JSON が読めない・キーが違う・`sum` が合わない・形が違う、のどれかなら**未命中として捨てる**（ファイルを消す）。再計算して上書きする。エラーは出さない。書き込みに失敗しても黙って続け、一時ファイルは消す。読めない（無い・ディレクトリ）は未命中で、消すものがない。

### 有効・無効

既定は**有効**（`check_cache.rs` の `DEFAULT_ON`）。`KSN_CHECK_CACHE=0` で無効、`1` で有効。第 1 段の既定を無効にしていた理由（パスごとにスロットが増え、上限がなかった）は、上の上限と削除で解消した。

### `check_recursion` の修正（常に有効）

関数ごとに呼び出しグラフを到達し直す実装は、関数数の 2 乗だった（3000 関数の鎖で約 3〜5 秒）。「自分自身へ戻れる」の判定を、強連結成分（Tarjan 法の反復版）と自己ループから 1 回で求める形にした。診断は変わらない（既存テスト全件とキャッシュの比較テストで確認）。

## 5. 正しさのテスト（`stage0/tests/cli.rs` の `check_cache_*`）

- `check_cache_is_on_by_default_and_can_be_turned_off`: `KSN_CHECK_CACHE` を書かなければ保存される。`0` なら何も書かない。
- `check_cache_limit_evicts_old_entries_and_keeps_results`: `KSN_CHECK_CACHE_MAX` を 1000 と 0 にすると、置き場の合計が上限以下になり、結果はキャッシュなしと一致する。上限が十分なら 9 本とも残る。
- `check_cache_parallel_processes_agree`: 同じ置き場を 8 本の `ksn check` が同時に使う。空から書く回・上限 500 で同時に削る回・命中しながら読む回の 4 通り。どの回もキャッシュなしと一致する。
- `check_cache::tests`（`check_cache.rs` のユニットテスト）: 更新時刻の古いものから消え、上限 0 でもディレクトリは残る（`trim_removes_oldest_first_until_under_limit`）。今の実行体でないものを先に消す（`trim_removes_other_executables_entries_first`）。記録を見て数え直すかを決める（`trim_counts_only_when_due`: 記録が無い・壊れている・上限超え・1 時間・時計が戻った、のとき数える）。
- `check_cache_entry_cap_is_enforced`: 件数の上限を超えたら件数が上限以下になる。`check_cache_record_avoids_recounting_on_every_run`: 1 時間以内の 2 回目の実行は記録の時刻を変えない。記録が壊れていたら作り直す。
- `check_cache_limit_evicts_old_entries_and_keeps_results` は使用量をブロック単位（4 KiB 切り上げ、記録を除く）で数え、上限 1000・0・3 ブロックのいずれでも上限以下になることを確かめる。
- `check_cache_matches_uncached_for_examples`: `examples/` の全パッケージで、無効・初回・2 回目の `check --json`（終了コードを含む）が一致する。
- `check_cache_matches_uncached_for_unsound_and_linear_ok`: `tests/data/unsound/` の全件と `linear_ok/` の全件。unsound は 3 本に 1 本が 3 通りの比較、残りは無効と初回の比較（時間の節約）。linear_ok は全件 3 通り。
- `check_cache_follows_edits_to_a_definition_and_its_dependents`: 2 ファイルのパッケージで、呼ばれる側の戻り値型・効果・名前・構文を順に変え、呼ぶ側の診断が変わるたびにキャッシュなしと一致する（命中時も確認）。
- `check_cache_survives_corruption`: 空・ゴミ・切り詰め・違う形の JSON・キーの書き換え・`data` だけの書き換え（`lint` を空にする・`skip` を反転する。`sum` が合わない）・スロットがディレクトリ、のどれでも結果が変わらず、次の実行で直る。

## 6. 計測（2026-11-13、Linux x86_64、各 1 回。他のジョブと同居しているので ±20% 程度の揺れがある）

`ksn check --json`、3000 関数・約 1.5 万行。基準は変更前の ksn。

| 構成 | 変更前 | キャッシュなし（修正後） | 初回（キャッシュ有効） | 全体が命中 | 1 行変更後（キャッシュ有効） | 1 行変更後の変更前 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 ファイルに 3000 関数 | 7.8 秒 | 4.4 秒 | 6.6 秒（同居の影響を含む） | 0.74 秒 | 4.5 秒 | 8.7 秒 |
| 30 ファイル × 100 関数 | 7.8 秒 | 3.8 秒 | 3.8 秒 | 0.63 秒 | 0.74 秒 | 7.3 秒 |

- `check_recursion` の修正だけで約 2 分の 1（7.8 → 3.8〜4.4 秒）。
- 変更のないファイルは全体を再利用できる（複数ファイルの 1 行変更で 0.74 秒）。
- **1 ファイルに全部ある場合、1 行変更はそのファイル全体の文面検査（lint 約 3.8 秒 + 文法 約 2.9 秒、いずれもファイルの大きさに比例）をやり直す**。定義単位にするには lint のうち定義をまたぐ規則（`order`、`unused` の `count_word`）を分けて、文法をトップレベルの定義ごとに切る必要がある（第 2 段）。

## 7. 第 3 段以降

1. （済み: 8 章）文面検査を定義単位に分ける。
2. 意味の検査: `TypeCk` が共有の表へ出す物（`let_tys` / `tytab` / `recv_log` / `edges` / `eff_checks` / `closure_asts`）を定義ごとに保存・復元できる形にし、2 章のキーで診断と一緒に保存する。キーの外部面（推論後の効果を含む）の計算が最初の作業。
3. `KSN_CHECK_CACHE` の既定を有効にする条件: スロットの上限・削除 → 済み（4 章の「上限と削除」）。`python3 tests/run_tests.py` の通過は統括者がマージ時に確かめる。
4. LSP（`analyze`）が同じ経路を通る。プロセス内のキャッシュ（`check --watch`）は段階 4 の 5。

## 8. 第 2 段: 文面検査を定義単位にする

実装は `lint.rs`（`Lint::run_memo`・`LintMemo`）、`grammar.rs`（`Grammar::check_memo`・`GramMemo`）、`check_cache.rs`（`FileMemo`）、`cli.rs` の `full_check`。意味の検査（2 章の外部面のキー）は保存しない（8.5）。

### 8.1 計測（第 2 段の前、1 ファイル 3000 関数）

文面検査（キャッシュなし）は文法 約 2.0 秒、lint 約 1.7 秒、整形（`format_source`）約 0.04 秒。この 3 つのうち、定義をまたぐ状態を持つ整形は安いので毎回やり、文法と lint を分ける。

### 8.2 lint: 定義ごとに閉じる検査と、そうでない検査

`Lint::run` は段ごとに `self.errs` へ積み、最後に `(行, コード)` で安定ソートする。段の順序と、同じ `(行, コード)` の診断の並びを変えないために、定義ごとの結果は**段ごとに分けて**保存し、`run_memo` が段の順に全定義を回して積み直す。結果（診断の列と順序）は `run` と完全に同じ（`lint::tests::memoized_lint_equals_whole_file_lint` が `run_whole` と比べる）。

| 段 | 扱い | 理由 |
| --- | --- | --- |
| `items`（定義への分割、`end` 名の食い違い、行頭でない行） | 毎回 | ファイルの線形走査。安い |
| `check_fqn_and_names`（FQN とモジュールの一致・命名） | **定義ごと**（段 0） | 定義の見出しとモジュール名だけを読む |
| `check_order`（E0020、定義の並び・群の順・`impls` の直前の `impl`） | 毎回 | 隣の定義との関係。「定義の見出しの列」全体の関数。キーに列を入れる代わりに毎回計算する（線形で安い） |
| `check_blank`（定義の間の空行、コメント直後の空行） | 毎回 | 隣の定義との間隔 |
| `check_attrs` の定義ごとの部分（`uses` / `derive` / `requires` / 境界の並び） | **定義ごと**（段 1） | 見出しの文字列だけを読む |
| `capture [..]` の並び | 毎回 | 行ごとの検査で、定義の外の行にもある。ファイル全体を 1 回走るだけ（正規表現を 1 回コンパイルして使い回す） |
| `check_indent` | **定義ごと**（段 2） | 定義の本体の行だけ |
| `check_names_and_unused`（命名・未使用の変数・引数・パターン束縛） | **定義ごと**（段 3） | 定義の見出しと本体だけ。lint の費用の大半 |
| `check_imports`（未使用 import、末尾名の衝突） | 毎回 | ファイル全体の文面（import 以外の全行）を読む。import の数だけの走査 |
| `check_pub`（`pub` が非 `pub` の型に言及） | 毎回 | 全定義の見出しを突き合わせる。非 `pub` の型の数 × `pub` の定義の数 |

定義ごとの結果のキー（`Lint::item_key`）: `H(モジュール名 ‖ .sig か ‖ キーワード ‖ 見出しの行 ‖ 見出しから `end` までの行数 ‖ 本体の行)`。段が読む `Item` の項目はこれだけ（`start`・`attached` は定義ごとの段では読まない）。`end` までの行数は本体が空のときの `end` の位置と「`end` が無い」場合を区別するために入れる。モジュール名が入るので、ファイルを移動（リネーム）すれば全定義が未命中になる。

**行番号**: 定義ごとの診断の行は**見出しの行を 1 とする相対**で保存する（`n - it.line`）。復元で `+ it.line` する。定義が下へずれても（上に行を足す・並べ替え）、定義の文面が同じなら同じキーで命中し、診断は新しい位置に出る。定義の外の診断（並び順・空行・import・`capture`）は毎回計算するので位置は常に新しい。

### 8.3 文法: 定義の規則への一致

`file` 規則は「定義のトークン列の連接」だけで書かれている（`import_line* (const|static)* (type|enum|trait)* extern* impl_only* fn_group* test*`）。定義の間にトークンは出ない（空行が BLANK になるのは定義の中だけ）。したがって、

- 各定義の行が自分の規則（`fn_def` / `type_def` / `import_line` など。見出しの語で決まる）に一致する、かつ
- 定義の種類の並びが群の順に合う（`impl` の行は、次が `fn` なら `fn` の群でもよい）、

なら `file` に一致する（十分条件）。`Grammar::check_memo` は、定義ごとに規則への一致を保存する（保存するのは**一致したものだけ**）。定義のトークンはその行・「次の意味のある行が `.` で始まるか」・直前の状態（`inside` と直前がコメントか。定義の境界では必ず偽）だけで決まる（`lex_lines`）ので、キーは `H(規則名 ‖ 次の意味のある行が . で始まるか ‖ 定義の行)` とし、命中した定義は**字句解析もしない**。

少しでも合わないとき（定義が規則に一致しない・分けられない行・コメントだけの末尾・並びの違反・字句エラー）は、**何も言わずファイル全体の `check` に任せる**。診断のメッセージと行（`near ..`、行は 1）は常にファイル全体の検査が決める（`memoized_grammar_equals_whole_file_grammar` が、元のファイルと行の変異で `check` と比べる）。事前検査（BOM・CR・タブ・行末の空白・行の長さ・末尾の改行）は毎回やる（安い）。

文法は位置を持たない（診断の行は常に 1 か 0）ので、行番号の扱いは要らない。

### 8.4 整形と `skip`

`format_source` は import の整理でファイル全体を見る（41 ms）ので毎回やる。`formatted != text` のときの `skip` の判定（整形後の lint が空で文法に一致する）も、`formatted` に対して同じ定義ごとの `run_memo` / `check_memo` を使うので、整形前後の両方の定義が同じ保存に入る。`skip` と lint の結果そのものは保存しない（第 1 段のファイル全体のキーは廃止）。

### 8.5 保存の形式とキー

スロットはファイルごとに 1 つ（`<KSN_CACHE_DIR>/check/<H(パス ‖ 相対パス)>.json`）。スロットの検証キーは `H(ksn 実行体 ‖ パス ‖ lint 用の相対パス)`（文面は入れない。定義ごとのキーが担う）。中身: `clean`（診断のない定義の 32 桁のキーを連ねた 1 本の文字列。大多数なのでパースを避ける）、`lint`（診断のある定義のキー → 4 段の診断）、`gram`（一致した定義のキーを連ねた文字列）。`sum` は `data` の SHA-256。

`store` は、今回の検査が**使った**キーだけを保存する（ファイルに無くなった定義の分は落ちるので、スロットはファイルの大きさに比例し続ける）。使ったキーの集合が読み込んだものと同じなら何も書かない。破損・不一致・形の違いは第 1 段と同じ扱い（捨てて再計算、エラーなし）。上限・LRU・並行の扱いも第 1 段のまま。

ksn 実行体の SHA-256（約 15 MB、約 0.1〜0.25 秒）は、全命中のときの下限として残る。

### 8.6 意味の検査を保存しなかった理由（余力の項目）

`borrowck.rs` の関数ごとの解析は、`TypeCk` が共有の表（`let_tys` / `tytab` / `recv_log` ほか）へ出す型の結果を読むので（3 章の表）、型推論の結果を保存・復元できる形にしないと外部面のキーだけでは決まらない。計測では意味の検査全体（`build_prog` + `Checker`）が 3000 関数で約 0.5〜0.8 秒で、全命中・1 行変更後の下限（約 0.8 秒）の大半はこの 2 つ。得るもの（最大 0.5 秒）に対し、過小無効化の危険（外部面の見落とし）が大きいので「迷ったら保存しない」に従い、第 3 段（型表の保存と外部面ハッシュ）の課題として残す。

### 8.7 正しさのテスト（`stage0/tests/cli.rs` と単体テスト）

第 1 段のキャッシュありなしの一致テスト一式はそのまま通る（破損テストだけ、保存の形に合わせて書き換える項目を変えた: `lint` 空・`skip` 反転 → `lint` 空・`gram` の偽造・`clean` の形の不正）。加えて:

- `check_cache_per_definition_edits_match_uncached`: 1 ファイルに const・型・関数・テストがある状態で、定義を 1 つ変える（診断の増減・命名・型の誤り）・上に行を足す（コメント・空行・const・本体への空行で、下の定義が全部ずれる）・並べ替える（入れ替え・逆順・戻す）・別の定義の外部面を変える（戻り値型・引数の数・効果・名前・型のフィールドの名前と型・const の型）・文面の誤り（二重の空白・タブ・`end` の欠落と名前違い・コメント直後の空行・末尾のごみ）、の各操作のたびに、同じ置き場を使い続けたキャッシュあり（位置を含む `--json`）がキャッシュなしと一致する。各ステップを 2 回（部分命中・全命中）。
- `check_cache_line_mutations_match_uncached`: 行の削除・複製・入れ替え・空行・コメント・字下げ・トークンの置換を、決まった乱数で 48 通り（1〜2 個重ねる）。6 通りごとに元に戻す。
- `lint::tests::memoized_lint_equals_whole_file_lint`（`examples/`・`tests/data/`・`bench/tasks/` の全 `.ksnl`、2 回目の全命中、別のモジュール名）と `grammar::memo_tests::memoized_grammar_equals_whole_file_grammar`（同じ集合と変異）。

## 9. 計測（第 2 段、2026-11-13、同居ジョブあり ±30% 程度）

`ksn check`（実時間、秒）。1 ファイル = 24,000 行・3000 関数（`m0.ksnl`）、30 ファイル = 30 × 100 関数。「第 1 段」は dev/plan の ksn、「第 2 段」はこのブランチ。

| 構成 | | キャッシュなし | 初回 | 全体が命中 | 1 行変更後 |
| --- | --- | --- | --- | --- | --- |
| 1 ファイル | 第 1 段 | 4.9 | 5.0 | 0.88 | **5.1** |
| 1 ファイル | 第 2 段 | 3.4 | 2.5 | 0.80 | **0.83** |
| 30 ファイル | 第 1 段 | 4.5 | 4.4 | 0.82 | 0.98 |
| 30 ファイル | 第 2 段 | 2.4 | 2.5 | 1.1 | 1.1 |

- 1 ファイルの 1 行変更後は約 6 分の 1（5.1 → 0.83 秒）。変更した定義 1 つだけを検査し直し、残りの下限は ksn 実行体のハッシュ・整形・定義のキーの計算・意味の検査（0.5〜0.8 秒）。
- キャッシュなしが速くなった（4.9 → 3.4 秒、30 ファイルは 4.5 → 2.4 秒）のは、lint が正規表現を検査のたびにコンパイルしていたのを 1 回にしたため（結果は同じ）。
- 30 ファイルの全命中は第 1 段と同程度（同居ジョブの揺れの範囲）。定義ごとのキーの計算（SHA-256）が増えた分と、整形を毎回やる分が加わるが、字句解析と lint の再計算が減る。


## 10. キャッシュの固定費（ksn 実行体の識別子）

### 原因

鍵の「ksn 実行体の中身」を、実行のたびに `current_exe` を読んで SHA-256 していた。ksn の実行体は約 15 MB で、これだけで約 50 ms かかる（この VM の `sha256sum` は 49 ms）。空の置き場でも全命中でも毎回払う。`KSN_TIMING=1` の `lint` の区間（キャッシュ有効・空の置き場）は約 116〜120 ms、無効のときは約 15 ms だった。

標準ライブラリはキーに入っていなかった（`load_std` は約 5 ms で、キャッシュとは無関係）。ここは原因ではない。

### 直したこと

`stage0/build.rs` がビルド時に `KSN_BUILD_ID`（SHA-256 の 64 桁）を作り、実行時は `env!` で読むだけにした（`check_cache::exe_key`）。入力は次のもの。

- `src/` の全ファイル（`include_str!` で埋め込む `.c` を含む）と `../spec/grammar.ebnf`（`grammar.rs` が埋め込み、文法の検査結果に効く）。
- `Cargo.toml` / `Cargo.lock` / `build.rs`、パッケージの版。
- `rustc -vV`、`CARGO_ENCODED_RUSTFLAGS`、`PROFILE` / `OPT_LEVEL` / `DEBUG` / `TARGET`、`KSN_VM_PROF`。

### 過小無効化にならない根拠

- 埋め込まれるソースか文法の 1 バイトが変わると識別子が変わる。確かめた: `src/check_cache.rs` に行を足して再ビルドすると識別子が変わり、元に戻すと元の値に戻る。
- ツールチェーン・フラグ・プロファイルが変わっても変わる。同じソースと同じツールチェーンなら同じ識別子で、その実行体の振る舞いは同じ。
- 前提として残るもの: 依存クレートの中身は `Cargo.lock`（チェックサム付き）で決まるとみなす。レジストリの中身を手で書き換えた場合は見ない。

「実行体の大きさと更新時刻を記録しておき、変わったときだけ計算する」方式は採らなかった。空の置き場の初回に結局計算するので、目標（空の置き場で差 30 ms 以内）を満たせないため。

### 計測（`examples/demo`、Linux、VM の Xeon E5-2620 v4）

| 構成 | 直す前（`lint` 区間, KSN_TIMING） | 直した後（`lint` 区間） | 直した後（プロセス全体, 5 回） |
| --- | --- | --- | --- |
| 空の置き場（初回） | 116〜120 ms | 約 16 ms | 約 39 ms |
| 全命中 | 97〜104 ms | 約 0.2 ms | 約 22 ms |
| 無効（`KSN_CHECK_CACHE=0`） | 約 15 ms | 約 16 ms | 約 38 ms |

空の置き場と無効の差は約 1〜2 ms（目標は 30 ms 以内）。全命中は無効より速い。直す前のプロセス全体の時間は、実行体を置き換えたあとに測り直していない。

### 残り

- `cli.rs` の `build_key`（`ksn build` のビルドキー）は実行体のバイト列をハッシュする。`ksn check` の経路ではないので変えていない。同じ方法に直せる。
