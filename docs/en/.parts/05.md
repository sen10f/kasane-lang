
#### Decision (stage 4, cancellation, 0.10.28)

This decides cancellation (f), carried over from stage 3. The suspension waiting on a wasm32 JS Promise (decision 5 of 5.6) is decided in a later stage, independently of cancellation (see "Remaining" below).

1. API: `std.task.Task<T>.cancel(self) -> ()` (`uses []`, `panics never`. Does not suspend). It consumes the value (`cancel(self)`). Canceling twice, or calling `join_task` after canceling, is E3002 for a moved value.
2. Meaning: a canceled task leaves its body at its suspension point (the place where it was stopped when canceled) and ends, with no result. A task canceled before it starts never runs its body. Cancellation is synchronous: by the time the canceling side returns, cancellation is complete. Cancellation does not change the order of the other tasks (round-robin, decision 4 of stage 1). The values in the frame of a canceled task are discarded without cleanup (release, linear obligations). That is why the check in 3 guarantees that a cancellable frame holds no value requiring release. Reading the result of a canceled task with `join_task` does not happen in terms of types (cancellation consumes the handle). As a defense, the executor has a panic "the task was cancelled".
3. Check (E4022, new. A conservative rule): `t.cancel()` passes only for the binding `t` of a `let t = std.task.spawn_local(closure)` that satisfies all of the following (and `t` is not reassigned or rebound within the same definition).
   - (a) The type of the closure's result (the `T` of `fn() -> T`) is a number, `bool`, `char`, unit, a reference, a tuple whose elements are all likewise, or `std.task.Task` (a value that is only a number).
   - (b) The types of bindings inside the closure (`let`, parameters, `match` arms, `for`) and of locals taken in by `move` are the same as (a) (those whose type is undetermined are not allowed).
   - (c) The closure does not call functions that can suspend (functions with `suspend` in `uses`. `std.task.yield_now` is a leaf, so it is allowed). A user function that does not suspend may be called if its result is of a type as in (a).
   - (d) Method calls inside the closure have only a receiver of `Task` or a numeric type (including `join_task`).
   - (e) If the handle to cancel is not a `let` binding (its provenance is unknown), such as an argument or a struct field, it is not allowed. The function form `std.task.Task.cancel(t)` is not handled, and only the method form `t.cancel()` passes.
   A violation is E4022 (`ksn check`. The same check for the tree walker and native). E4022 looks only at the single point of cancellation, so the `spawn_local` side can be written normally (tasks that hold values requiring release can also be created; they just cannot be canceled).
4. Implementation: when the tree walker receives the canceled task's signal, it unwinds the body with `Err(Ctl::Cancel)` (not an error) and returns a signal to the canceling side. Natively, the executor `ksn.task.cancel` releases the leaf frame the task is waiting on (the frames of `yield_now` and `join_task`) and the task's frame, and sets the state to "canceled" (3). An entry of the executor's table becomes 40 bytes, and the field `[32]` records "the leaf frame currently being waited on" (a leaf frame is a child frame held by the parent frame, and cannot be fully released by the parent frame alone).
5. Remaining (stage 5 and later): widening the conditions for cancellability (releasing values requiring release by cleanup at each suspension point), checks that go beyond the provenance of handles (handles across function boundaries and in struct fields), and whether to make `Task<T>` linear.

#### Decision (stage 5, await_js, 0.10.29)

This implements the suspension waiting on a wasm32 JS Promise (decision 5 of 5.6). `std.task.await_js(handle: u32) -> i32 uses [suspend] panics never` is added (`spec/stdlib/std/task.sig`). Waiting for JS completion can be done only outside the executor, so the caller of `block_on` is included in the state machine as a suspension point. A "wait" is added to the return value of `ksn_main`, and an ABI is introduced in which JS calls a resume export after completion. The existing event-driven SPA (`apps/todo_spa`, the form of `ksn_fetch_done`) is not changed.

1. API: `std.task.await_js(handle: u32) -> i32 uses [suspend] panics never`. `handle` is a number identifying a Promise made on the JS side (returned by JS imports such as `ksn_timer_start`). The result is the `i32` that JS passes with `ksn_resume(handle, value)`. `uses [suspend]` is required, and it can be used only on wasm32 (panic/E9040 in the tree walker and native).
2. ABI: the wasm32 entry `ksn_main() -> i32` returns the exit code when the program has ended (0 for normal, 1 for Err, 101 for panic, etc.), and -1 when waiting for JS completion. When the awaited Promise resolves, JS calls `ksn_resume(handle: i32, value: i32) -> i32`. Its return value follows the same convention, and while it is -1 the wait continues. `ksn_resume` is exported and can be called from JS.
3. Shape of the executor: `block_on` is converted to `ksn.task.run.new` / `ksn.task.run.poll`, and `poll` returns `true` if all tasks are complete, and `false` if there is a task waiting for JS completion (the implementation of `ksn.task.run.poll` judges whether there is a wait with `ksn.task.js_waiting`). The entry wrapper function (the function of the original key of `ksn_main`) returns -1 if a wait remains after the first `poll` (the ABI of `ksn_main`). Resumption repeats the same shape: `ksn_resume` → `ksn.js.put` (put the result in the storage) → `.resume` (advance the frame) → `.pending` (whether a wait remains).
4. Storage: a global array `ksn.js.tab` (16 entries, 24 bytes each: `u32` state, `usize` handle, `i32` value) temporarily holds the results of JS completion waits. `ksn.js.put` writes the handle and value into a free entry. `ksn.task.await.poll` (the leaf suspension point) takes out the value of its own handle with `ksn.js.take`, sets the frame's state to "complete", and returns `true`.
5. Check: `await_js` can be used only on wasm32 (only when `ptrwidth` is 32). In the tree walker it panics (exit code 101) with the reason "there is no JS counterpart". A native `--release` build stops with E9040 (`std.task.await_js can be used only in wasm32 builds`). `ksn check` passes it for the wasm32 target.

## 6. Compilation and cache

- The unit of compilation is the function.
- Each definition has an "external surface". For a function it is the header; for `type` / `enum` / `trait`, the whole definition (including fields and layout); for generic functions and `const fn`, the whole definition; for `const` / `static`, the whole definition; for `impl`, the whole line. The external surface of a `panics never` function with `stack` omitted includes the stack upper bound computed by the compiler (when the upper bound changes, dependents are re-checked).
- Cache key = the function's own definition hash + the external-surface hashes of its transitive dependencies. When a generic calls a generic, this is also included transitively.
- Monomorphization results are cached by (function, type arguments, the key above) and deduplicated at link time.
- Debug builds (`ksn build` without `--release`) do not do inter-function inlining. Release builds also transitively include the definition hashes of inlined callees in the key.
- The cache has a size limit (default 2 GiB, overridable with the environment variable `KSN_CACHE_MAX`, evicted by LRU). Intermediate representations are not stored, only the generated artifacts.
- The cache key also includes the target, compiler version, edition, build kind, and optimization settings.

### 7.1 Diagnostics

- Fixed error codes `Exxxx`. Ranges: E0xxx lexical and syntax, E1xxx names, modules, and visibility, E2xxx types and traits, E3xxx ownership, borrowing, and linear types, E4xxx side effects, panics, and stack, E5xxx `unsafe` permission, E9xxx tools and packages. The explanation of each code is authoritatively given by `ksn explain`.
- One line of JSON is `{"code":"E0001","fatal":true,"fqn":"...","file":"...","line":1,"col":1,"message":"...","fix":[{"file":"...","line":1,"col":1,"end_line":1,"end_col":10,"replace":"..."}]}`. The range of `fix` is a half-open interval, `line` and `col` are 1-based, and `col` is in units of Unicode scalar values. An insertion has start = end. If there is no fix, `fix` is an empty array. A diagnostic outside a definition has `"fqn": null`.
- The order of diagnostics is stable: file path → line → column → code.

### 7.2 WASM ABI (`wasm32-unknown-unknown`, 0.10.14)

`ksn build --target wasm32-unknown-unknown` turns LLVM IR into a bare `.wasm` with clang (wasm32) and `wasm-ld` (`target/wasm32-unknown-unknown/<debug|release>/<name>.wasm`). The triple selects `wasm32-unknown-unknown`. The browser is the main target and WASI is not needed (files, sockets, and time are not given a form that pushes them outside, and unsupported things are stopped with a reason). When WASI is needed, use `wasm32-wasi` (see "The WASI section" below).

- The pointer width is 32 bits. `usize` / `isize` / raw pointers / references are i32, and `size_of` follows (4.5). The data layout is `e-m:e-p:32:32-…-ni:1:10:20`.
- Imports are the two of `env` (only the ones used are attached), and imports of JS functions (see "Connecting with JS" below):
  - `ksn_write(fd: i32, ptr: i32, len: i32) -> i32`: writes `[ptr, ptr+len)` of linear memory to `fd` (1 = standard output, 2 = standard error). Returns the number of bytes written, negative on failure. Output such as `std.io.print_line`, panic messages, and `Error: …` go out through this.
  - `ksn_exit(code: i32)`: exits. Does not return (it does not return to the caller, and the host receives the exit code).
- There are two kinds of exports:
  - `memory`: the linear memory. Allocation is `malloc` / `realloc` / `free` on top of it (first-fit with a free list, extended by `memory.grow`. The upper limit is up to the host).
  - `ksn_main() -> i32`: the entry. The return value is the exit code.
  - Functions whose name begins with `ksn_` (the last component of the FQN. `ksn_rt_` and `ksn_main` are reserved): exported under that name (`wasm-export-name`). They can be called from JS (event receivers, etc.). Arguments and return values are only integers, pointers, `bool`, and `()` (structs are not allowed, E9040). Two functions with the same name are E9040.
- Connecting with JS (修正プラン 5-3): the `link "env:name"` of a Kasane `extern` becomes an import of JS's `env.name` (wasm32 only. On other triples it fails with a reason). The shape of the declaration is `extern app.dom.create(tag_ptr: *const u8, tag_len: usize) -> u32 link "env:ksn_dom_create"`. Arguments and return values are limited to ABI scalars of integers, pointers, `bool`, and `()`. Strings are passed as two arguments `(ptr: *const u8, len: usize)` (UTF-8, in linear memory). When JS returns a string to Kasane, it writes into the region `(ptr, cap)` passed by the caller and returns the length written (the form `ksn bindgen` generates). `link "env:name"` is not linking of a C function, so `ksn check` passes it but `ksn build` (native) does not resolve it.
- `ksn bindgen <definition file>` (修正プラン 5-3): from a definition file (one specification per line. Lines of `module` / `ksnl` / `js` / an optional `prefix` / `op <name>` are placed. `#` is an annotation), it makes Kasane `extern`s (`<module>.raw_<operation>`, `link "env:<prefix><operation>"`), safe functions called inside `unsafe` (`<module>.<operation>`, `pub`), and JS glue code (`makeImports(host)`). The built-in operations are creating DOM elements, attributes, text, adding and removing children, `listen` (calls `ksn_event(tag)`), input values, `localStorage` get / set, and `fetch` (completion is `ksn_fetch_done(tag, status)`, and the body is read with `fetch_body`). The generated module is put in `[unsafe] modules`. A definition error gives exit code 2 with a line number (nothing is written).
- Suspension waiting on a JS Promise (`await_js`, stage 5 of 5.6, stage 4 of 修正プラン 4-1): when `std.task.await_js(handle: u32) -> i32 uses [suspend] panics never` can be used, the wasm32 entry and resume export take the following form.
  - Entry `ksn_main() -> i32`: after the first `poll`, returns -1 (wait) if there is a task waiting for JS completion. If there is no waiting task (the program has ended), the usual exit code (0 / 1 / 101 / 102).
  - Resume export `ksn_resume(handle: i32, value: i32) -> i32`: passes the result of the Promise JS was waiting for and resumes. The return value is the same as `ksn_main` (-1 for waiting, the exit code on completion). When the program has already ended (ended normally, or called `ksn_exit` through a panic, etc.), it does nothing and returns -2 (the runner ignores this value and does not treat it as an exit code).
  - Storage: inside the executor `ksn.js.tab` (a global array, 16 entries) is used, and the result JS passed with `ksn_resume` is temporarily saved with `ksn.js.put`. The leaf suspension point `ksn.task.await.poll` takes out the value of its own handle with `ksn.js.take`.
