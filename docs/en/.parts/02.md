### 3.3 Extraction and references

```
# Fetch a whole definition (fn / type / enum / trait / test. ksn get is authoritative). The name is directly followed by one of ( [ space end-of-line
find src -name '*.ksn[lh]' -exec awk '/^(fn|type|enum|trait|test) app\.net\.Header([ (\[]|$)/,/^end app\.net\.Header$/' {} +

# const / static / extern
grep -rhE --include='*.ksn[lh]' '^(const|static|extern) app\.net\.MAX_LEN[: (]' src/

# List of signatures
grep -rhE --include='*.ksn[lh]' '^fn ' src/

# List of methods of a type
grep -rhE --include='*.ksn[lh]' '^fn app\.net\.Header\.' src/

# Call sites (the only authority)
ksn refs app.net.parse_header
```

- Every line of the body is indented (except blank lines) and no raw newline enters a string, so range extraction by `^end` holds.
- `import` is one module per line: `import app.net`. Only per-module imports; per-item imports and aliases are forbidden. To use the short form `net.parse_header(` an `import` is needed. An FQN (`app.net.parse_header(`) can be used without `import`, but only if that package is the own package or a dependency in `kasane.toml`. An `import`ed module counts as used if anywhere in the file (header or body) refers to it by short form or FQN, and it is an unused import (E1020) only when nothing refers to it.
- The only things that match the short form `net.parse_header(` in grep are function calls. Method calls, references through traits (FQNs of the form `core.cmp.Ord.i32.cmp`), `blanket`, `impl` lines, and references via generics cannot be enumerated by the grep above, so `ksn get` / `ksn refs` are the only authority.
- All grep examples are written in ERE (`-E`) (BRE `\|` is not used because GNU and BSD behave differently).
- Definitions of transitive dependencies (packages that are not direct dependencies) cannot be written as FQNs, but are subject to type inference and method resolution.
- Two modules whose trailing names collide cannot both be `import`ed in the same file (E1111). Do not `import` either; use them by FQN.
- Canonical form: references to types and traits inside a definition header are always FQNs (independent of imports; the header alone determines the meaning). The exception is the prelude (4.2). In bodies, use the short form for functions, types, constants, and variants of `import`ed other modules. Definitions of the same module are always referenced by FQN (a module cannot `import` itself).
- There is one reference form (principle 5). Writing a type or trait of an `import`ed module in a header with the short form (`net.Header`), or writing a definition of an `import`ed module in a body with the FQN (`app.net.parse_header(`), is an error (it differs from the output of `ksn fmt`, so E0020. E1117 is abolished). Both, however, resolve to the same definition. `ksn fmt` brings them to the canonical form: short forms in headers to FQNs, and FQNs of `import`ed modules in bodies to short forms. An FQN in a body of a module that is not `import`ed is already canonical, so it is not changed (no `import` is added). An FQN also remains as an FQN when its first component could collide with a local binding of the same function (when it appears as a bare identifier). An `import` that, as a result of formatting, is no longer referenced from the body (one that only the header referenced) is deleted by `ksn fmt`. An `import` referenced from nowhere is a semantic error (E1020), so it is not deleted and `check` reports it. `fmt --check` and `check` report a non-canonical form as the same error (E0020).
- Resolution order (the same for headers and bodies): the first component `a` of a name `a.b.c` is looked up in this order: (1) local bindings of the function (variables and parameters of the body. If it matches, it is a reference to the local value, not a module reference), (2) generic parameters (header), (3) the trailing name of an `import` (the `net` of `import app.net`. If it matches, it expands to `app.net`), (4) otherwise, as an FQN. Prelude names (4.2) are one-component names and do not collide with module names. A local binding with the same name as the trailing name of an `import` is shadowing (E1021, 4.1), and two `import`s whose trailing names collide are E1111 (rejected at the `import`), so the same name is never resolved to different definitions in a header and a body. A short form in a header is an undefined type (E1102) if the file's `import`s have no such first component.
- `import` lines are grouped at the start of the file and sorted in dictionary order.

### 3.4 Line-leading keywords

Only `fn` `type` `enum` `trait` `impl` `const` `static` `extern` `test` `end` `import`. Since one file = one module, `mod` is abolished.

### 3.5 Extensions and the `unsafe` permission

- Source extensions are `.ksnl` (`l` for language) and `.ksnh` (`h` for human). `.ksnl` is the canonical form without comments, and the LLM writes only this. `.ksnh` is `.ksnl` plus only comment lines (`//`, `///`). Humans write `.ksnh`, and `ksn strip` (and also `ksn fmt`) deletes lines whose first non-whitespace is `//` and produces the adjacent `.ksnl` (the single blank line right after the comment block at the start of the file is deleted together). `src/x.ksnh` and `src/x.ksnl` are placed side by side and both are committed. In a module that has a `.ksnh`, the `.ksnh` is authoritative, and `ksn check` verifies that the `strip` of the `.ksnh` is byte-identical to the `.ksnl` (a mismatch, or a missing `.ksnl`, is E9050). Writing a comment in `.ksnl` is E0059. Diagnostics are displayed at the lines of the `.ksnh`, and in `--json`, `file` and `line` are the lines of the `.ksnl` and `ksnh_line` is the line of the `.ksnh`. What is distributed, what is subject to `hash`, and what `ksn vendor` copies is only `.ksnl`; the `.ksnh` of dependencies is not read, and E9050 is not checked for them (`ksn publish` verifies that the `.ksnh` of the root package matches the `.ksnl`, and uses only `.ksnl` for distribution and `hash`. A library package to be published has only `.ksnl`, and `.ksnh` stays in the author's repository). A module without a `.ksnh` has only `.ksnl`. After an LLM changes a `.ksnl`, `ksn sync [module]` re-attaches the comments of the human's `.ksnh` onto the new `.ksnl`, tying them to the FQNs of definitions and the statements of bodies (comments of vanished statements and definitions are reported one by one and the `.ksnh` is not written. `--drop-lost` discards them, and `--keep-lost` leaves them right before the definition as `// LOST (vanished <FQN>): ...`. If a human also changed the same definition, it stops as a conflict, and `--take ksnh|ksnl` chooses). There is no distinction of layers (high-level / low-level).
- The only modules that can use `unsafe`, FFI (`extern`), syscalls, raw pointers, and direct allocator manipulation are those listed in `[unsafe] modules` of `kasane.toml` (8.1). The listing is an exact match, or a prefix match where `a.b` includes `a.b.c`. Use in a module without permission is E5001.
- The purpose is "being able to audit the location of dangerous code in one place, `kasane.toml`". The permissions of dependency packages are also visible in their `kasane.toml`.
- `core` / `alloc` / `std` (bundled packages, 8.2) are implicitly permitted.
- The permission is not a reference rule: definitions of a permitted module can be referenced normally from any other module. The function side bears the responsibility that its header's `uses` / `panics` cover them (3.8).
- Since one file = one module, a single module cannot have several files (a duplicate is an error).

### 3.6 Modules and FQNs

- The source root is `src/`. The file corresponding to module name `a.b` is `src/a/b.ksnl`. The file `src/a.ksnl` of module `a` can coexist with a directory `src/a/` of the same name. The file name (excluding the extension) is a `snake_case` identifier and must not be a reserved word (primitive type names are allowed. 3.7).
- The package name must match the top-level component (every module of package `app` begins with `app` or `app.`).
- `tests` cannot be used as the second component of a module name in `src/` (`app.tests` and `app.tests.*` are reserved for the integration tests of `tests/`. 3.2. A violation is E1121).
- The FQNs of all definitions in a file begin with the module name (3.2).
- The FQN separator is `.`. Components are ASCII identifiers (3.7).
- Cycles are forbidden (an error). Cycle detection treats all of `import`, FQN references in bodies, and FQN references in definition headers as edges between modules (references to prelude names (4.2) and method resolution into the home modules of primitive types (`core.num` / `core.bool` / `core.char` / `core.str` / `core.slice` / `core.array`) are not counted as edges). Mutual recursion across modules is not possible (only within the same module).
- `entry` is specified by `[package] entry` of `kasane.toml` (8.1), and is a function FQN within the own package (e.g. `app.main`. The file is `src/app.ksnl`). If omitted, the package is a library, and `ksn run` is E9030. `ksn new` generates `entry = "<name>.main"`.

### 3.7 Lexical structure

- UTF-8 (no BOM. Invalid UTF-8 is E0007, a BOM is E0004), newlines are LF only. Tabs, trailing whitespace, and extra blank lines at the end of a file are forbidden. A file ends with exactly one LF.
- The line length limit is 100 characters (the number of Unicode scalar values). A line that exceeds it is E0055 (pointing at the column of the 101st character). The following are exempt: (a) lines whose beginning, excluding indentation, is a line-leading keyword (`fn` `type` `enum` `trait` `impl` `const` `static` `extern` `test` `import` `end`) (including signature lines in trait bodies), and (b) lines containing a string literal (an excess due to a single token that cannot be resolved by wrapping). (a) also includes lines beginning with the closure expression `fn(...)` (because parameter lists are not wrapped).
- Comments are only standalone lines beginning with `//` (there are no end-of-line comments or block comments). Comments can be written only in `.ksnh` (3.5). Placing one in `.ksnl` is E0059.
- The spacing between tokens within a line is determined by a table, `ksn fmt` fixes it, and `ksn check` makes any difference E0020 (leading indentation is separate, in units of 4 spaces). Spacing is only 0 or 1. The first matching rule from the top is used: (1) if the next is `)` `]` `,` `;` `?` `.` `::` `:`, then 0; (2) if the previous is `(` `[` `.` `::`, a prefix operator (`&` `*` `-` `!`; also the `mut` of `&mut` and the `const` of `*const`), or the `<` of type arguments, then 0; (3) if the next is the `<` or `>` of type arguments, then 0; (4) if `{` and `}` are adjacent, then 0; otherwise 1 after `{`, before `}`, and before `{`; (5) when the next is `(` or `[`: if the previous is the head of a call or index (a name, `)` `]` `?`, the `>` closing type arguments, `self` `Self`, `impl[`), then 0; `fn(` (a closure) is also 0; otherwise (reserved words, `,`, binary operators, after `derive [` `capture [` `requires`) 1; (6) everything else is 1 (both sides of binary operators and `->` `=>` `=`, between words). Whether `-` `*` `&` is prefix or binary is decided by whether the previous token ends a value (a name, a literal, `)` `]` `}` `?` `self`, etc.), and `<` is a type-argument bracket only when the previous token is a type name (UpperCamelCase containing lowercase letters) or `::` (a `<` in an expression is a comparison). `- 1i32` (whitespace between `-` and the digits) is a form where the prefix operator and the number are separated, so it is rewritten to `-1i32`.
- Identifiers are ASCII. Functions, variables, modules, and fields are `snake_case` (one leading `_` is allowed. The unused marker of 4.6), types, traits, and variants are `UpperCamelCase`, and `const` / `static` are `SCREAMING_SNAKE_CASE` (only uppercase letters, digits, and `_`; `_` is not required). A naming-convention violation is an error. Reserved words cannot be used as definition names or binding names. However, primitive type names (including `str`) are allowed as intermediate components of an FQN, module names, and file names, and `blanket` is allowed only as an intermediate FQN component (`core.num.i32.checked_add`, `src/core/bool.ksnl`). `self` can be used only as a parameter name and in expression position, and `Self` only in type position. `UpperCamelCase` does not contain two or more consecutive uppercase letters (`HttpServer`). Digits attach to the preceding word (in both `UpperCamelCase` and `snake_case`, a word starts with a letter. `foo2` is allowed, `foo_2` is not).
- Integer literals: `1_000` `0xff` `0b1010` `0o17`, type suffix (`10u8`). Without a suffix, if the type is not determined by context, it is an error. Hex digits and `0x` etc. allow only lowercase (uppercase is E0002. `ksn fmt` does not rewrite it). The digit separator `_` can be placed only at positions every 3 digits in decimal and every 4 or 2 digits in hex, binary, and octal (within one literal the group width is uniform; only the topmost group may be shorter), and not at the start, at the end, or consecutively. Whether to use separators is optional, but for decimals of 5 or more digits `ksn fmt` inserts `_` every 3 digits (`100_000u32`). The choice of radix, type suffix, and escape is not rewritten (an exception to principle 5). `_` cannot be used in floating-point literals.
- Literals of signed integer types may have a leading `-` (`-1` `-0x10i32`). This is part of the literal token and not an operator, and no whitespace can be placed between `-` and the digits. A negative literal for an unsigned type is an error.
- Floating point: `1.0` `1e-3` (`1.` and `.5` are not allowed), suffix `f32` / `f64`. Without a suffix, if it is not determined by context, it is an error.
- Strings are `"..."` and `char` is `'a'`. Escapes are `\n` `\t` `\r` `\\` `\0`, in `char` `\'`, and in strings `\"`, `\xHH`, `\u{H...}`. `\xHH` is `00`–`7F` in normal strings and `char`, and `00`–`FF` in `b"..."` and `b'..'` (u8). `\u{...}` is 1 to 6 hex digits, and surrogates are not allowed. Byte strings are `b"..."`.
- There is one way to write characters and escapes (principle 5. G38). (1) There are characters that cannot be written as-is anywhere in the source (in strings, characters, comments, or `///`) (E0004): characters that change display direction (U+202A–202E, U+2066–2069, U+200E, U+200F, U+061C), invisible and control characters (Cc other than LF, Cf, Zl, Zp, Co, Cn, and U+FEFF including a BOM in the middle), and non-ASCII whitespace (Zs). When needed in a literal, write `\u{202e}`. (2) The escapes of strings and `char` are only: `\\`, `\"` in strings, `\'` in `char`, the named `\n` `\t` `\r` `\0`, and `\u{..}` for representing the characters of (1) (hex in lowercase, no leading 0). Printable characters are written as they are (`"\x41"`, `"\u{41}"`, `"\u{3042}"` are E0005. Fixed by `ksn fix`). Normal strings and `char` have no `\xHH`, and `\xHH` is written only for the unprintable bytes of `b".."` / `b'..'` (those of 0x00–0x1f that have no name, and 0x7f–0xff) (lowercase hex). (3) Strings and comments are in Unicode normalization form NFC (E0006. Fixed by `ksn fix`). The displays of `ksn doc`, `ksn get`, etc. output the characters of (1) in the form `<U+202E>`.
- Reserved words: in addition to the line-leading keywords, `let` `mut` `if` `else` `match` `loop` `while` `for` `in` `break` `continue` `return` `true` `false` `self` `Self` `pub` `uses` `panics` `unsafe` `move` `with` `dyn` `blanket` `const` `never` `may` and the primitive type names (4.5). `stack` `impls` `derive` `linear` `layout` `requires` `capture` `link` `close` `is` are contextual keywords with special meaning only in headers, closures, `extern`, `with` expressions (4.4), and comparison position (`expr is pattern`. 4.1), and can also be used as identifiers (variable, parameter, and field names). Reserved for the future: `async` `await` `where` `ref` `as`.

### 3.8 External functions and raw pointers (`unsafe`-permitted modules only)

- An external function declaration is one line: `extern app.sys.getpid() -> i32 link "getpid"` (if `link` is omitted, the trailing name of the FQN). C ABI only. Calls are possible only inside an `unsafe` block.
- `extern` functions and `core.ptr` functions are not treated as values. They can be written only in the function position of a call (`t.getpid()`), and referring to them as values (`let f = t.getpid`, assignment to a field, passing as an argument or return value, capture by a closure, an `if let` binding) is E5003 both inside and outside `unsafe` (decision of 2026-11-15. Chapter 9). Callbacks passed to C are out of scope, since a Kasane function or a closure expression is written as the actual argument (below).
- Raw pointers `*const T` / `*mut T` can be used only in `unsafe`-permitted modules (3.5), and dereferencing and pointer arithmetic are limited to inside `unsafe` blocks.
- The side effects and panics of external calls and raw-pointer operations inside an `unsafe` block are the responsibility of the function side, to be covered by `uses` / `panics` of the enclosing function's header (the header is the only authority). Therefore, a function of an `unsafe`-permitted module can declare `uses [io.fs]` etc., and can be called from other modules too. There is no side-effect name `ffi`. There is also no `unsafe fn`.
- Creation, conversion, reading, and writing of raw pointers are done with `core.ptr` (`add` `add_const` `as_const` `as_mut` `cast` `cast_const` `from_mut` `from_ref` `is_null` `null_mut` `read` `write`), and calls only inside `unsafe` blocks. `add_const` and `cast_const` are versions of `add` / `cast` that take `*const` and return `*const`, used to add or convert while staying const under the rule that a `*const` cannot be passed to `*mut` (passing a `*const` to `add` / `cast` is E2023). There is no conversion to or from integers. `*const` → `*mut` (`as_mut`) is allowed only inside `unsafe` in an `unsafe`-permitted module, and responsibility for data races is declared by a manual `impl` of `Send` / `Sync`. A type with interior mutability either holds a raw pointer (and so ceases to be `Send` / `Sync` by automatic derivation), or states the conditions explicitly with a manual `impl` of `Send` / `Sync`. The atomic types of `core.sync` are the only exception that is automatically `Send` + `Sync` with only integer fields (built-in interior mutability), and can be placed in the `static` of 3.2.
- Dynamic loading: `link "library:name"` (e.g. `extern app.sys.cbrt(x: f64) -> f64 link "libm.so.6:cbrt"`) opens a shared library at run time with `dlopen` (`LoadLibraryA` on Windows), looks up `name` with `dlsym` (`GetProcAddress`), and calls it. The separator is the last `:` (if there is no `:`, it is the static `link` above). Library name resolution follows the OS rules (a path if it contains `/`, otherwise the search path). Resolution happens at the first call (`ksn check` does not load it), and the result is remembered. If it cannot be loaded or the symbol is missing, it is treated like a panic: `panic: cannot load the shared library ...` (or `symbol ... was not found in ...`) is written to standard error and the exit code is 101. The same in the interpreter and native generation. `LoadLibrary` on Windows is implemented but unverified.
- The C libraries to link are specified in `[native]` of `kasane.toml` (8.1. `static` is the path of a static archive, `dynamic` is the library name for `-l`, and `search` is the directories to search at link time. Relative paths are from the package root. An unknown key is E9007, a malformed shape is E9012). The static `link` (without `:`) of `extern` is resolved within this, and native generation (`ksn build`, the LLVM side of `ksn test --both`) links the real thing (`--emit-llvm` does not link). Archives are placed after the referrer and `-L` before. wasm32 cannot have C libraries, so a `[native]` is E9040, and `--backend c` also does not link, so E9040. In the interpreter (`ksn run`), the `dynamic` libraries are searched by `dlopen` (the file name is `lib<name>.so` (`lib<name>.dylib` on macOS, `<name>.dll` on Windows), otherwise one in a `search` directory. Static archives cannot be read, so the diagnostic for a missing symbol directs you to `ksn build`). The `[native]` of dependency packages is not used for linking (adding links stays an explicit act of the user), and is recorded in `kasane.lock` and compared (additions and removals are E9060 / E9062). To search `dynamic` libraries at run time, they must be installed together, or the environment side must prepare things such as `LD_LIBRARY_PATH` (`search` is the link-time search location, and no rpath is added).
- Callbacks (C calls Kasane): an `extern` parameter can be written with a function type `fn(*const i32, *const i32) -> i32 uses [] panics never`, and as the actual argument a Kasane function (non-generic. `app.compare`) or a closure expression with `capture []` is passed. To C, the C-ABI entry of that function is passed as a function pointer. Function types that cross the C boundary are limited to `uses [] panics never`: since C can carry neither side effects nor panics, if the effects of the function type written in the `extern` header differ it is E5004, and if the function or closure passed is not `uses [] panics never` (including inferred effects) it is E5005. The parameters and return values of callbacks are integers, floating point, `bool`, `char`, raw pointers, `()`, and `layout c` structs passed by value (following the INTEGER / SSE / MEMORY classification of x86_64 System V AMD64. The interpreter supports only x86_64 Linux, with a named error at run time on other hosts. Native generation supports only x86_64). User data (`void *`) passes a raw-pointer argument straight through: if the C API passes `void *user`, declare the same raw pointer type naming the pointee type (`*mut app.Acc`) in both the `extern` and the callback (`void *` and `T *` are identical in the C ABI). The caller passes it with `core.ptr.from_mut(&mut acc)`, and the callback updates the state with `core.ptr.read` / `write`. An API without user data (`qsort`) needs only the callback. Callbacks do not panic (`panics never`), so unwinding never crosses a C frame. Stack overflow (5.2) is outside the guarantee of `panics never`, and stops the process without unwinding across C frames (the interpreter exits with code 102 and `stack overflow`).
- To pass a closure with captures to a C callback, use `core.ffi.trampoline` (it takes `closure: &mut F` and returns `(fn(*mut (), A) -> R uses [] panics never, *mut ())`). What can be passed to a function-typed parameter of `extern` is a `capture []` closure or a plain `fn`; a closure with captures cannot be passed as is (E5005). Pass the returned function pointer to the C callback and the `*mut ()` to the C `void *user`. The lifetime of the user-data pointer is only the duration of the `extern` call into C, and C must not keep or refer to it after returning from the call.
- `core.ptr.from_mut` / `from_ref` on an array, slice, or `Vec` creates a `*mut T` / `*const T` pointing at the first element (the form for passing an array to C). Before and after the C call, the original value and the memory visible to C are synchronized (interpreter).
- A type with C-compatible layout gets `layout c` on its `type` header (`enum` and generics are not allowed, E5006). The layout is exactly the rules of the target's C ABI: fields are placed in declaration order, each at its natural alignment (same as the size. `i8` / `u8` / `bool` are 1, `i16` / `u16` are 2, `i32` / `u32` / `f32` / `char` are 4, `i64` / `u64` / `isize` / `usize` / `f64` / raw pointers / function types are 8), gaps are filled with padding, and the overall size is rounded up to a multiple of the largest alignment. Fields are limited to these scalars, nested `layout c` structs, and fixed-length arrays `[T; N]` (elements are C types) (E5006). There are no empty structs (because C has none). A type that is not `layout c` has unspecified layout and cannot be used in the parameters or return values of `extern` (E5007). What can be used in the parameters and return values of `extern` are integers, floating point, `bool`, `char`, raw pointers, function types, and `layout c` structs (passed and returned by value); arrays cannot be passed by value (use a pointer).
- Passing structs by value follows the x86_64 System V AMD64 classification: a struct of 16 bytes or less is classified per 8 bytes as INTEGER (including integers and pointers) or SSE (only `f32` / `f64`) and passed in registers (6 GP, 8 XMM), and if there are not enough, the whole struct is passed in the argument area (stack). A struct larger than 16 bytes is MEMORY (copied to the argument area), and returning by value takes the address of the return destination as a hidden argument. Passing by pointer (`*mut T`) passes only the address. Both the interpreter and native generation support this on x86_64 Linux. On AArch64 Linux (`--target aarch64-linux-gnu`, AAPCS64), `extern`s with scalar integers, pointers, and floating point can be called (the interpreter calls by the AAPCS64 rules, and native generation leaves it to clang's calling convention). Passing and returning structs by value are both unsupported and give a named reason (native generation: `extern <name>: passing a struct by value is native-supported on x86_64 only`. In the interpreter, the `extern` call is a named run-time error). `extern` callbacks (passing a Kasane function to C) are supported only on x86_64 Linux in the interpreter. A struct with a fixed-length array is supported by the interpreter, and native generation skips it with a reason (waiting for native support for array types).
- There is no upper limit on the number of arguments: integers, pointers, and `bool` are assigned to GP registers, `f32` / `f64` to XMM registers, and the overflow is passed on the stack (the interpreter also performs calls with the same rule itself on x86_64 Linux, with no limit of 6 or 8). The interpreter on hosts other than x86_64 Linux supports up to 6 integers, pointers, or floating-point values (a call beyond that is a named run-time error). A callback can receive up to 6 integers or pointers and 8 floating-point values (interpreter), and the interpreter can hold up to 64 distinct callbacks at the same time.
