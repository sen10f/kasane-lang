## 5. Strictness

### 5.1 Side effects and panics

- A function header declares `uses [...]` and `panics never | may`. An undeclared side effect or panic is an error. `uses` and `panics` cannot be omitted on any function (E4020). The declaration must match the effects of the body exactly (E4025, 0.10.32): the effects of the body are the union of the declared effects of the callees (including closure bodies), plus the `panics may` from integer arithmetic and indexing, and being either too broad or too narrow is an error (too narrow is, as before, E4001 / E4002 / E4003 / E4004). The reason: if a declaration is made broad and communication etc. is added to the body later, it would slip past the public signature and effects recorded in a dependency's lock. Only the methods of trait implementations (`impls`) are matched not against the body but against the effects promised on the `impl` line (the trait's declaration instantiated with the actual arguments of the `impl` line) (a violation is E4025). Bodies whose callees are not determined (methods with several candidates of differing effects, wrappers that call `extern`, etc.) are not checked for a match. `ksn fix` rewrites the declaration.
- The standard side-effect hierarchy (there are no user-defined side effects): `io` (`io.fs` `io.net` `io.console`), `time`, `rand`, `thread`, `suspend` (suspension. 5.6), `alloc`, `env` (environment variables and command-line arguments), and `process` (process control including `std.process.exit`). `[]` means no side effects.
- `alloc` refers only to allocation (`alloc` / `realloc`). Deallocation is not a side effect. A type that owns heap memory has the allocator (or its handle) as a field, and Drop deallocates through it. The `dealloc` of the allocator trait requires `uses [] panics never`.
- Side effects have a hierarchy (`io` includes `io.fs`, `io.net`, etc.). A function with fewer side effects can be passed where more side effects are allowed (subtyping). `panics never` is a subtype of `panics may`.
- `dyn Tr<E0, P0>` is a subtype of `dyn Tr<E, P>` when `E0 ⊆ E` and `P0 ⊑ P`, and it can be converted behind `&` / `&mut`. The function type `fn(A) -> R uses [E] panics P` is covariant on the return side and contravariant for function types in arguments.
- The signature of an impl's method must match the trait's declaration (a violation is E1122). The signature obtained by replacing `Self` in the trait's declaration with the impl's target type, and the trait's type parameters with the actual arguments of the `impl` line, is compared with the number of arguments, the form of the receiver `self` (`&Self` / `&mut Self` / `Self`), the type of each argument, and the return type. When the method itself has type parameters, the type comparison is limited to the number of arguments and the presence of a receiver. Effects (`uses` / `panics`) are looked at by E4021 in the next item.
- The effects of an impl's method must not exceed the effects of the trait declaration (a violation is E4021). For a method `m` of `impl Tr for X`: (1) each concrete name in the `uses` of `m` is covered by one of the `uses` of the trait's declaration of `m` (following the subtyping of the hierarchy: if the declaration is `io`, the impl may have `io.fs` or `io`; if the declaration is `io.console`, the impl cannot have `io`). Effect variables on the impl side are not compared. (2) If the trait's `m` is `panics never`, the impl is also `panics never` (by `never ⊑ may`, a `panics may` impl is not allowed). The trait's effect variables and panic variables are replaced with the actual arguments of the `impl` line (the `[io.fs]` and `never` of `impl core.iter.Iterator<T, [io.fs], never> for X`) before comparing. When an effect variable that cannot be bound by the actual arguments remains in the declaration, that comparison is not done (silent). It is also not done when the trait method's declaration has no `uses` / `panics`. A trait method signature cannot have `stack`, so no impl rule is made for the upper bound of `stack`.
- Types that hold an allocator with its type erased (`std.sync.Sender` / `Receiver`) require `A: Allocator + Send + 'static` at creation, and deallocation is done by `Drop` with the type-erased allocator.
- A function type has both `uses` and `panics` in its type: `fn(T) -> U uses [E] panics P`. `dyn Tr` is allowed only when all methods of `Tr` and its supertraits have no generics and do not use `Self` by value in arguments or return values (the type parameter is `Sized`, and `dyn` appears only behind `&` / `&mut`. For `x.m()` with `x: &dyn Tr`, the methods of `Tr` and its supertraits are searched. A violation is E2033. `&Self` behind a reference, and passing `Self` as an argument of a supertrait, are also not allowed. Therefore `Fn` `FnMut` `FnOnce` `Copy` `Clone` `Eq` `Ord` `Hash` cannot be `dyn`, and closures with environments are received through generics, not `dyn`). Trait objects receive effects through the trait's type arguments: `dyn std.net.Handler<[io.net], never> + 'static` (the illustrative `trait std.net.Handler[E: uses, P: panics]` has `fn handle(self: &Self, req: &[u8]) -> Result<(), std.net.Error> uses [E] panics P`, with no generics and no by-value `Self`, so it can be `dyn`).
- A call through `dyn Tr<E, P>` has the effects of the declaration `uses [E] panics P` of `Tr`'s method, instantiated with the type arguments of the `dyn` (the `handle` of `dyn std.net.Handler<[io.net], never>` is `uses [io.net] panics never`). If the caller's `uses` / `panics` do not cover it, it is E4001 / E4002, the same for `&dyn` / `&mut dyn` / `Box<dyn>`. The effects of the actual `impl` side fall within what the trait's type arguments cover (the covariance of 4.3), so this is the upper bound.
- As the owned version of `dyn`, `alloc.boxed.Box<dyn Tr<E, P> + 'static, A>` is provided (for holding type-erased values, as in framework extension points and event handlers. With generics alone, code increases per instantiation). `dyn` can be written only behind `&` / `&mut` and in the first type argument of `alloc.boxed.Box`, and writing it directly elsewhere (type arguments of other types, fields, elements of `Vec`, etc.) is E2047 (`Vec<Box<dyn ..>>` is allowed). The lifetime bound of a `dyn` put in a `Box` is only `'static`, and omission or another lifetime is E2047. The `dyn`-safety rules (above) are unchanged (a violation is E2033).
  - The conversion is not implicit (it is not added to the table of 4.2), and is explicit with `alloc.boxed.Box.into_dyn(b)`: it turns a `Box<T, A>` where `T: Tr` (the `impl`s of `Tr` and its supertraits are in place) and `T` has no references (`'static`) into a `Box<dyn Tr<E, P> + 'static, A>` with the same allocator `A`. The target type is determined by the expression's expected type (`let` annotation, argument, return value, field) (if it cannot be determined, E2044). It is E2046 if the target is not a `dyn`, if `T` does not implement `Tr`, or if `T` has references. The reason it is not implicit: the conversion erases the type of the allocated value and changes the treatment of effects (`E` / `P`) and ownership, so we keep the 4.2 principle that "implicit behavior is only what is in the table". The typical use (`Box.new` → `into_dyn` → `push`) takes the addition of one expression, and since the expected type is required, the burden of type annotations does not increase.
  - `x.m()` on a `Box<dyn Tr>` searches the methods of `Tr` and its supertraits (auto-dereference of the receiver. 4.2). `as_ref` / `as_mut` return `&dyn Tr` / `&mut dyn Tr`, and `into_inner` cannot be called when `T` is `dyn` (E2046).
  - Destruction runs the drop glue of the held concrete type (destruction of fields and the `Drop` implementation), and then deallocates with the allocator `A` the `Box` holds (exactly once). A linear type cannot be put in a `Box` (8.3. The `T` of `Box<T, A>` is non-linear). `Send` / `Sync` are in 5.5.
- When processing is executed later, as in iterators, the side effects and panics belong to the side that actually executes (the `uses` / `panics` of `next`).

```
impl[I: core.iter.Iterator<T, E, P>, F: core.ops.Fn<(T,), U, E, P>, T, U, E: uses, P: panics] core.iter.Iterator<U, E, P> for core.iter.Map<I, F, T, U, E, P>
fn core.iter.Map.next[I: core.iter.Iterator<T, E, P>, F: core.ops.Fn<(T,), U, E, P>, T, U, E: uses, P: panics](self: &mut core.iter.Map<I, F, T, U, E, P>) -> Option<U> uses [E] panics P impls core.iter.Iterator<U, E, P>
    ...
end core.iter.Map.next

fn core.iter.map[I: core.iter.Iterator<T, E, P>, F: core.ops.Fn<(T,), U, E, P>, T, U, E: uses, P: panics](it: I, f: F) -> core.iter.Map<I, F, T, U, E, P> uses [] panics never pub
    ...
end core.iter.map
```

(Because ordering is by UTF-8 byte sequence, `core.iter.Map.next` (`M`) comes before `core.iter.map` (`m`).)

### 5.2 Behavior of panics

- `panics never` guarantees that no explicit panic (`core.panic.panic`), no call of a `panics may` function, and no out-of-range index occurs. OOM is returned as a `Result` and so is not a panic. Deadlock detection (exit code 101), resource exhaustion, and the call-depth limit (exit code 102) are outside this guarantee (5.2, 5.3).
- A panic does not unwind (the `close` expression of `with` is not executed either. 4.4). It writes the message to standard error and aborts the process immediately (exit code 101. Deadlock detection also gives exit code 101, but that detection is outside the promise of `panics never`, 5.2). It cannot be caught. A panic inside a thread also aborts the whole process. Drop does not run during a panic. This is compatible with the constraint that Drop is `panics never` (4.4).
- Stack overflow is not a panic (101) but a stop at a resource limit due to the call-depth limit (`stack overflow` on standard error, exit code 102. The limit value is in 5.3), and is outside the guarantee of `panics never`. The same applies when it occurs inside a callback called from C (3.8): it stops the process without unwinding across C frames.

### 5.3 Stack and recursion

- If a `panics never` function recurses (including mutual recursion and recursion through `dyn` / function pointers), the header requires `stack <bytes>` (example: `... panics never stack 4096`). The compiler statically computes the maximum stack usage of the call graph rooted at that function, and it is a compile error if it exceeds the declared value. For indirect calls, all functions whose callee `uses` and `panics` match (in the subtyping sense) are candidates for the computation (for calls through `&dyn` / `Box<dyn>`, the corresponding method of every `impl` of that trait is a candidate).
- The call-depth limit (0.10.31): in all execution engines (tree walker, VM, KIR reference executor, native (LLVM), wasm32), when a call is about to start such that the number of simultaneously live calls (counting the entry `main` as the first) would exceed **100000**, the process writes `stack overflow` to standard error and stops with exit code 102. It stops in the same way at the same depth regardless of the engine (counted per thread, and `spawn`ed threads have the same limit). Calls up to the 100000th, including the entry, pass. This stop is not a panic (101) but a stop at a resource limit, and is outside the promise of `panics never` (5.2). `stack N` is a declaration of an upper bound on the frame of a single call (stack usage), and does not guarantee depth (even with a small `stack` value, if the depth reaches 100000 it stops with 102). The native main thread reserves a stack of 1 GiB or more and `spawn`ed threads 64 MiB (reservation of virtual memory), and if the frame is about 8 KiB or less per call, the main thread suffices up to the limit depth (the largest frame of the recursive descent in `selfhost/` is about 5 KiB). The shadow stack of wasm32 is reserved at 256 MiB, but the JS engine's own call stack (about 1 MB for node's main thread) is outside the implementation, and if it runs out first it is a trap (the bundled executors `tools/wasm/run.mjs` / `run_wasi.mjs` run in a Worker with a 512 MiB stack). The tree walker also stops with the same 102 when the Rust stack looks about to run out (the depth may be shallower than the limit). How to change the depth limit from within a program is in the next item.
- There are only two ways to change the depth limit (0.10.32. The decision and reasons are in `設計_深さの上限.md`). (1) `depth M` in the header of the entry (the function pointed to by `entry` in `kasane.toml`) (after `stack N`. `M` is an integer from 1 to 10000000, and out of range is E4015): the main thread's limit becomes `M` (the default when omitted is 100000). Writing it on a function other than the entry, or on a library function, is E4014. (2) A `spawn`ed thread keeps the default limit of 100000, and only threads that need to go deeper raise it with `std.thread.spawn_deep(allocator, f, depth)` (the same type as `spawn`, and the third argument `depth: usize` is that thread's limit, clamped to 1 to 10000000). A task of `std.task.spawn_local` uses the limit of the thread that created the task. The way depth is counted is the same as above (per thread, calls up to exactly the limit pass). The stack size is determined from the limit: for the main thread `max(1 GiB, M × 8 KiB + 64 MiB)`, and for `spawn`ed threads 64 MiB (`depth × 8 KiB + 64 MiB` for `spawn_deep`). If a function whose single frame greatly exceeds 8 KiB recurses deeply, the OS stack would run out before the depth limit, so native and the tree walker check the remaining stack (1 MiB short of the bottom) and stop with `stack overflow` and exit code 102 before it runs out (never a SIGSEGV). The VM and the KIR reference executor do not push call frames onto the OS stack, so only the depth limit applies.
- `stack` can be written only on recursive `panics never` functions. Writing it anywhere else is E4011. The stack upper bound of non-recursive functions is computed by the compiler and included in the external surface (6).
- Drop glue for types containing recursion is not generated automatically. Recursive types require an explicit implementation of Drop, and without it E4013. Since Drop is `uses []` and cannot allocate, the implementation is done by tearing down with `unsafe` in an `unsafe`-permitted module, or by an index (arena) representation.
- `derive [Drop]` (4.3) has the implementation generate the destruction of self-recursive types (recursion only through `Box<Self>` / `Option<Box<Self>>`), satisfying E4013. The generated destruction is iterative, makes no recursive calls and no allocation, so it does not exhaust the stack regardless of the depth of trees and linked lists (even at one million), and there is no allocation failure. The procedure: destroy the non-recursive owned fields of the value as usual, and collect the child `Box<Self>`s (k of them). If k = 0, return the node's allocation and go to the next item on the work list; if k = 1, return the allocation and proceed to that child; if k ≥ 2, descend into the first child and write the remaining k − 1 into the node's allocation itself (whose contents have been read) as a "work frame" and push it onto the work list (when the frame becomes empty, return the allocation). The work list is placed inside the parents' allocations, so neither a `Vec` nor allocation failure is needed, and destruction stays `uses [] panics never`. The order of destruction is unspecified (unobservable: non-linear, and `Drop` cannot have effects). Recursion through `Vec<Self>` etc. and mutual recursion are out of scope (E2051). For those, use a hand-written `Drop` (`unsafe`) or an index (arena) representation. Implementation: the tree walker and the VM use the engine's value destruction, and KIR / LLVM use the per-type helper function `drop.<FQN>` (`kir_lower_drop.rs`. Natively, types with `Box<Self>` in an `enum` payload can be lowered. A type with an `Option<Box<Self>>` field is outside KIR and falls back to the bundle).

### 5.4 Other

- There are no warnings. Unused variables, parameters, and imports are also errors.
- Only for `ksn run`, however, unused-class errors (unused variables, parameters, imports) are output as diagnostics with `"fatal": false` and execution continues. The exit code in this case follows the program's. They are always fatal in `ksn check` / `build` / `test`. Release builds are always strict.
- New checks are enabled only in the next edition. However, fixes of soundness (holes in borrow checking and type checking) apply immediately.
- `unsafe` is only a named block inside a permitted module (3.5). A reason string is required: `unsafe "name" "reason" { ... }`.

### 5.4.1 Scope of Edition 1 (frozen and experimental)

Edition 1 freezes only the core of the implementation.

- Frozen: the language specification (syntax, types, ownership, effects, etc.), the core standard library (the range of `core` / `alloc` / `std` that is settled in Edition 1), and the tools `check` / `run` / `test` / `build` / `fmt` / `fix` and the LSP. The execution engines are the VM and LLVM native.
- Experimental and outside Edition 1: `ui/` (UI), the WASM SPA, the package registry / `publish`, self-hosting (stage1/stage2), and bindgen. These are not part of the Edition 1 contract and will be considered in v1 and later.

### 5.5 Threads

- The marker traits `core.marker.Send` / `core.marker.Sync` have no body and are derived automatically (`Send` if all fields, variant payloads, tuple elements, and array elements are `Send`, and likewise `Sync`). `&T` is `Send` when `T: Sync`, `&mut T` is `Send` when `T: Send`, and `&T` / `&mut T` are `Sync` when `T: Sync`. `dyn Tr` is `Send` / `Sync` only when the `requires` of `Tr` include `core.marker.Send` / `Sync` (`alloc.boxed.Box<dyn Tr, A>` has the same condition, and also when `A` is `Send` / `Sync`. The manual `impl` of `alloc.boxed` can take `dyn` as `T`, so it is stated by this rule). Raw pointers are neither. Primitive types, `()`, `!`, `&str`, and function pointers are `Send` + `Sync`, and `[T]` / `[T; N]` follow `T`. A closure is `Send` / `Sync` when the actual types of its captures (`&a` is `&T`, `&mut a` is `&mut T`, `move a` is `T`) are all `Send` / `Sync`. The judgment for recursive types regards a cycle as holding (coinductive). The `requires` of `dyn Tr` trace supertraits transitively. These follow the automatic-implementation rule of 4.2. `alloc.arena.Handle<T>` is a value of only a `usize` and a `u32`, so it is automatically `Send` + `Sync` (by itself it grants no access), and `alloc.arena.Arena<T, A>` holds a `Buf` (raw pointer), so automatic derivation does not hold, and it is stated by the manual `impl` in `spec/stdlib/alloc/arena.sig` (when `T` and `A` are `Send` / `Sync`).
- `fn std.thread.spawn[A: alloc.alloc.Allocator + core.marker.Send + 'static, F: core.marker.Send + core.ops.FnOnce<(), T, E, P> + 'static, T: core.marker.Send + 'static, E: uses, P: panics](allocator: A, f: F) -> Result<std.thread.JoinHandle<T, A>, std.thread.SpawnError<F>> uses [alloc, thread, E] panics P pub` (allocation is stated explicitly by the allocator argument. 4.1. For a thread that wants a higher call-depth limit, `std.thread.spawn_deep(allocator, f, depth: usize)` of the same type. 5.3). The closure's effects `E` and panic `P` are borne by the caller of `spawn`. `JoinHandle<T, A>` is a linear type, consumed by `join(self)` (`uses [thread] panics never`. Because a panic inside a thread aborts the process. 5.2). Allocation failure and thread-creation failure are returned as `SpawnError<F>`. `SpawnError<F>` (fields `code: i32` and the closure passed in, `closure: F`) returns the closure, so if the closure took in a linear value (`File`, a socket, etc.), `SpawnError<F>` is also linear, and the `Err` arm must take out `closure` and consume it (discarding it is E3003).
  - A value passed to a position with a `'static` bound (an argument of `&'static T`, an argument whose type contains the types of type parameters `F` / `T` with `'static` bounds. Including `f` of `spawn` / `spawn_local`) must be either of a type that cannot contain local borrows, or of a provenance known to be `'static` (string literals, `const`, results of functions returning `&'static`, `&'static` arguments, and aliases of these); a violation is E2037. A closure that captures `&a` / `&mut a`, a type with references, the type of a type parameter without a `'static` bound, and a value whose type is undetermined are regarded as possibly containing local borrows (fail-closed). The same holds even when the callee goes through a closure variable or a wrapper function.
- Moving linear values between threads: the `F` and `T` of `spawn`, and the `T` of `channel`, permit `linear` (`spawn[.., F: linear + .., T: linear + ..]`). (1) The obligation of a linear value taken with `capture [move x, ..]` moves to the closure, and the closure body must consume the linear value on all paths (the general rule for closures. 4.4. Not consuming is E3003). (2) When the closure returns a linear value, `JoinHandle<T, A>` carries the obligation of `T`, and `join` returns `T` to the caller (a value received by `join` is an ordinary linear binding). `JoinHandle` is linear to begin with, so a thread that is not `join`ed is reported as a leak.
- Channels: `channel[T: linear, ..]` can carry linear values. `Sender<T>.send` consumes the value (when the receiver was dropped and the send could not be made, the value comes back as `Err(SendError { value })`. The owner handles the value). `Receiver<T>.recv` returns a value. (1) `Sender<T>` is non-linear whether `T` is linear or not and may be dropped (the owner of values remaining in the queue is the receiver, and dropping the sender only means "no more will be sent"). (2) By the type-argument rule (4.4), `Receiver<T>` is linear when `T` is linear, and when `T` is non-linear `Drop` destroys the remaining values as before. A linear `Receiver<T>` is consumed with `Receiver.close(self) -> Result<(), Receiver<T>>`. `close`, if other receivers remain, folds up its own share and gives `Ok(())`; if it is the last receiver and the queue is empty, it closes the end (later `send`s are `Err`) and gives `Ok(())`; if it is the last receiver and values remain in the queue, it does not close and returns that receiver with `Err(self)` (the caller receives and handles the rest with `recv`, and then calls `close` again). A container-returning `close(self) -> Vec<T>` is not adopted because it contradicts the fact that containers cannot hold linear values (8.3). By making it a retry form that forces the caller to handle the remaining values, neither leaks nor double frees occur structurally. The decision to close and the check that the queue is empty are made together in one step under the channel's internal lock.
- Duplicating senders and receivers: `Sender.clone(self: &Sender<T>) -> Sender<T>` and `Receiver.clone(self: &Receiver<T>) -> Receiver<T>`. Both only add an end to the same channel and do not allocate (they count the end's reference count), so they are called `clone` and not by the convention for duplication that may fail to allocate (`try_clone`, 8.3). The side whose end reference count becomes 0 is regarded as "closed": when all senders are dropped, `recv` on an empty queue is `Err`, and when all receivers are dropped (including by `close`), `send` is `Err`. Duplicating the receiver lets several threads compete for work from one queue (each value goes to only one of the receivers).
- Bound checking (0.10.37): for a user's generic `Send` / `Sync` bound such as `fn w[T: core.marker.Send](x: T)`, the caller checks the type of the actual argument by the same rule as `spawn` (a type containing raw pointers, etc., is E2030). A manual `impl[T: core.marker.Send] core.marker.Send for W<T>` for a generic type writes the same marker bound on the type parameter (E5008).
- Shared state (worker pool): mutable state shared by several threads (example: a store) is placed in a `static` `std.sync.Mutex<T>` (0.10.36). `T` may be a number or a struct (one holding `Vec` / `String` / `HashMap`), the initial value is written as a call of a `const fn` with no arguments and is evaluated only once at the first `lock` (`static app.STORE: std.sync.Mutex<app.Store> = std.sync.Mutex.new(app.mk())`). State that is read often uses `std.sync.RwLock<T>` (`read` → `get`, `write` → `get` / `get_mut`). A reference cannot be carried out of a guard (E3030). If the same thread re-acquires a lock it already holds, it is a deadlock in every execution path (101, outside the promise of `panics never`). Shared ownership (`Arc`) is not added to the language. A form that puts one piece of state in a capacity-1 channel and passes it around (take it with `recv` and return it with `send` when done) is also correct, but jams when workers increase, so it is not recommended. A group of workers takes work from a work channel (sharing a duplicated receiver).
- Capacity (0.10.39): the `capacity` of `channel(allocator, capacity)` is the upper bound on waiting elements (0 is treated as 1). `send` waits while the queue is full until `recv` makes room or all receivers are dropped (in which case `Err(SendError { value })`) (the same as Rust's `sync_channel`). If all waiters are waiting, it is a deadlock (101, outside the promise of `panics never`, `send() on a full channel ...`).
- The meaning of the two executions (decision 2026-11-14. The same program of `spawn` / `join` / channels runs in one of the following two ways depending on the execution path):
- Deterministic cooperative execution (the tree walker of `ksn run`, `ksn test`, the VM): threads are not run at `spawn` time, and are run one at a time to completion, from the waiting side, at `join` and at `recv` on an empty queue (while a sender is alive) (no preemption). The order of running is determined by a fixed rule, so the same program gives the same result however many times it is run, and tests are deterministic. Because a running thread is not interrupted, a program that makes no progress whichever thread runs first (such as round-trip request and response) becomes a `deadlock` panic (exit code 101). A pool that puts all accepted connections in, drops the sender, and then `join`s gives the same result as native with this method.
- Real threads (native of `ksn build`, LLVM): an OS thread (pthread) is created for each `spawn` and run concurrently. There is no fixed upper limit on the number of threads (if one cannot be created, `SpawnError<F>`). Scheduling is nondeterministic, and the order may change on each run.
- Capacity and the meaning of execution (0.10.39): with real threads, a `send` on a full channel actually waits. Cooperative execution (tree walker, KIR executor) can hold values beyond the capacity, instead of waiting, only while there is a pending thread or while the frame above is stopped at a `recv` on the same channel (the receiver will eventually pull them out, so the order of values is the same).
- Otherwise (when there is neither a pending thread nor a receiver waiting on the same channel; including waiting in `join` or `recv` on another channel), a `send` on a full channel is a deadlock (101, outside the promise of `panics never`), as with real threads.
- Results of correct programs: for a program without data races (mutable shared values are passed through `Mutex` or channels and pass the `Send` / `Sync` check), if the result (standard output, exit code, values received by `join`) does not depend on scheduling, the two executions give the same result. The pool example above is this case.
- Forms whose result depends on scheduling: even without data races, the results of the two executions can differ. (1) A form that progresses in cooperative execution and whose result can change with real threads: two threads each `print_line` and are then `join`ed. Cooperative execution outputs in `join` order (creation order), and real threads output from whichever ran first. Both are correct executions. (2) A form that does not progress in cooperative execution but does with real threads: the main thread sends a request to a worker, receives the reply, and then sends the next request (a round trip). In cooperative execution, once the worker starts running it cannot complete while waiting for the next request, so it is a `deadlock`. With real threads it progresses. Likewise, a form in which the accept loop does not `join` the workers until it reaches a count limit gives no replies until the end in cooperative execution, and replies concurrently with real threads.
- Forms whose result depends on scheduling (capacity, 0.10.39): when cooperative execution meets a `send` on a full channel and a pending thread remains, it continues beyond the capacity. With real threads, if none of those threads `recv`s from this channel it is a deadlock (101, outside the promise of `panics never`). The difference is visible only in programs that deadlock with real threads.
- Capacity 0 is treated as 1 (it is not a rendezvous).
- `ksn test --both`: compares the result of the tree walker (cooperative execution) with the result of the LLVM executable (real threads), and reports a mismatch as FAILED. Therefore only tests whose results do not depend on scheduling can be compared. A test that depends on scheduling gives a mismatch even if the program is correct. Write tests so that the order of output is determined by `join` or `recv`. The form of (2) shows up as a mismatch: the tree walker gets a `deadlock` panic and LLVM gets a result that progressed.
- Implementations of interior mutability, and manual `impl`s of `core.marker.Send` / `Sync`, can be written only in `unsafe`-permitted modules (a violation is E5002). A manual `impl` of `Send` / `Sync` can be written only in the module that defines that type (an `impl` for a type of another module or package, or a standard type, is E5010; an `impl` for a type for which it holds automatically, such as a type whose fields are all numbers, `bool`, or `char`, is E5011; a double `impl` for the same type is E1114. The standard library itself is excluded). Atomic types are provided by `core.sync`. `alloc.boxed` / `alloc.vec` / `alloc.collections` / `alloc.arena`, and `std.sync` / `std.thread`, which hold raw pointers, state `Send` / `Sync` by this rule (example: `impl[T: core.marker.Send, A: alloc.alloc.Allocator + core.marker.Send] core.marker.Send for alloc.vec.Vec<T, A>`). For traits that have a manual `impl`, the manual `impl` is used instead of automatic derivation. A type holding references (`std.sync.MutexGuard`) states the conditions under which sharing is safe with a manual `impl` of `Sync` (`T: Sync`).

### 5.6 Suspension `suspend` (decision 2026-11-14. The decision and implementation of stage 1 are in 0.10.15)

Asynchrony is introduced not by `async` / `await` and the coloring of functions, but by the effect `suspend` (this decision replaces the "will not build" of `設計プラン.md` 3.1). `async` / `await` remain reserved words, and are not introduced as syntax.

- Effect: `suspend` is added to the standard side-effect hierarchy (5.1). `suspend` is a leaf effect alongside `io` and others, and has no hierarchy. Its meaning is "execution may be suspended in the middle of a call and resumed later". A function with `uses []` does not suspend.
- Which functions can suspend: only functions whose header has `uses [suspend, ..]` and functions that call them (by the union of effects, including inference). Following the ordinary effect rules, a function with `suspend` can be called only from a function with `suspend` (or an effect variable `E` that allows it). If not covered, E4001 (5.1). The inference of non-`pub` functions (5.1) also includes `suspend` in the union by the same rule. The subtyping is `uses [] ⊆ uses [suspend]`, so a function that does not suspend can be passed where suspension is possible. The reverse is not allowed, and real-time paths can shut out suspension with `uses []`.
- Suspension points: a call expression of a function with `suspend` is a suspension point. Suspension points are visible as call positions (no marker syntax like `await` is added. The `uses` of the called function is the visible information). `panics never` and `suspend` are independent, and a suspension point does not panic.
- Executor: the scheduler that holds suspended computations and resumes them is held by the standard library (`std`). The language defines only the effect `suspend` and the meaning of suspension points, and the executor's API is defined in the normative signatures of `std` (8.3) (see "Decision (stage 1)" below).
- Implementation policy (not specification but guidance for implementation): natively, the executor puts tasks on top of real threads (5.5), and suspension points return I/O waits to the executor. On WASM (wasm32), the browser's event loop is outside the executor, and waits such as `fetch` return to JS at suspension points and resume through the completion callback. The aim is that the same Kasane source runs on both. Suspension points are converted to a state machine (decided and implemented in stage 2 (0.10.18). `設計_KIR.md` chapter 26).
- Relation to linear types and borrows: values that live across a suspension point are saved in the task's state. (1) Linear values keep their obligation even when saved (discarding the values of a frame without cleanup on cancellation is limited to frames that hold no value requiring release (E4022), so no obligation is lost during suspension. The ordinary rules such as E3003 apply as they are). (2) A `&` / `&mut` borrow that spans a suspension point is E3050 (see decision (stage 1) 3). A form in which the binding of a lock guard (the guard of `MutexGuard` / `RwLock` read and write) is used after a suspension point is also E3050 (`core.mem.drop` the guard before the suspension point). The cancellation check E4022 also looks at the types of bindings inside closures, and of temporaries of non-Copy structs, arrays, and tuples (also in argument position).
- Relation to `Send`: if a task may move between the executor's threads, all values that live across suspension points must be `Send` (5.5). WASM is single-threaded, so `Send` is not required.
- Multi-threaded executor (0.10.41): `std.task.block_on_threads(allocator, n, f)` runs the root task `f` on `n` workers (including the calling thread), and returns the result when `f` has finished and all tasks have finished (the same structuring as `block_on`). Tasks are created with `std.task.spawn(f)` (only inside `block_on_threads`. Calling it confusingly in place of `spawn_local` inside `block_on` is a run-time panic). As with `std.thread.spawn`, `A` / `F` / `T` are `core.marker.Send + 'static`, it is E2040 if the captures and results are not `Send`, and E2037 / E3060 if a local borrow is carried out. A task may move between threads at every suspension, so the locals that live across suspension points of functions called (by the transitive closure of calls) from the tasks of `spawn` / `block_on_threads` must be `Send` (**E2074**. A type parameter needs `T: core.marker.Send`. When the type is undetermined, it is an error on the conservative side). The entries are separated because whether `Send` is required (work that holds non-`Send` values uses `block_on` + `spawn_local`) is a difference in meaning. The deterministic cooperative execution (tree walker, KIR reference executor) ignores `n` and runs in round-robin in id order, the same as `block_on` (the `Send` check is the same). Programs whose results do not depend on scheduling give the same result in every execution path (5.5). Windows and wasm32 native are supported (wasm32 is `wasm32-unknown-unknown` / `wasm32-wasi`). macOS is not supported (targets outside cross-compilation are E9040). Cancellation (`Task.cancel`) discards a task that has not started yet immediately, and a task running on another worker stops at its next suspension point (0.10.42. It is not stopped while running).
- Implementation status: stage 1 (the scope of "Decision (stage 1)" below) was implemented in the VM (`ksn run` and `ksn test` default to the VM, `--engine=tree` for the tree walker, and entries that cannot be lowered fall back silently) (0.10.15). Stage 2 (0.10.18) also implemented native (KIR / LLVM) and wasm32. A function with `uses [suspend]` is converted into a state machine that can be resumed at each suspension point (a call of a function that can suspend) (frames are placed in the `heap` region, and values that span suspension points are saved in the frame). The executor is written in KIR, and lowers `block_on` / `spawn_local` / `yield_now` / `join_task` (設計_KIR.md chapter 26). The output and exit code are the same as the tree walker. Stage 3 (0.10.21) made it possible to put `Result` in a frame, and what remains as E9040 natively is only a `Result` inside an `Option` (`Option<Result<..>>`. A LLVM constraint that the wrapper's aggregate cannot have a `Result` field) and types that cannot be put in a frame. A `block_on` result of the form `Option<Result<..>>` also remains E9040 for the same reason.

#### Decision (stage 1, 0.10.15)

Of the open points, those needed for stage 1 are decided as follows. The points carried over to stage 2 and later are listed at the end.

1. The executor and API (`std.task`, normative signatures in 8.3). A single cooperative executor: tasks are created with `spawn_local`, results are received with `join_task`, and `yield_now` yields to other tasks.
   - `std.task.block_on(f) -> T`: runs `f` as the root task. After `f` finishes, it waits for all tasks that have not yet finished, and then returns `T` (structured). `uses [E]` (the effects of `f`), `panics may`. Nesting is not allowed (run-time panic).
   - `std.task.spawn_local(f) -> std.task.Task<T>`: creates a task. It runs inside `block_on`, when other tasks yield or wait. `f` is `'static`, `uses [E]`, `panics may` (calling it outside the executor is a run-time panic).
   - The fields of `std.task.Task<T>` are private, and users cannot create one (the same as the descriptor of `TcpStream`). `Task` holds the generation of the `block_on` that created it, and calling `join_task` / `cancel` in a different `block_on` is a run-time panic.
   - `std.task.yield_now()`: `uses [suspend]`. Yields if there are other runnable tasks. Does nothing outside the executor.
   - `Task<T>.join_task(self) -> T`: `uses [suspend]`, `panics may` (a circular wait is a deadlock panic). It is not named `join` because it could not be distinguished by name from `std.thread.JoinHandle.join` (which does not suspend) (the borrow checker's judgments are made by name).
2. The handle `Task<T>` is not linear in stage 1. It need not be `join_task`ed, and is always completed at the end of `block_on` (there is no cancellation. `cancel` was added in stage 4 (0.10.28). See "Decision (stage 4)" below). Whether to make it linear is decided in stage 2.
3. Borrows across suspension (E3050, new). A borrow that is used after a suspension point (a call of a function with `uses [suspend]`. For functions, the `uses` of the resolved definition; for methods, it is regarded as a suspension point if any of the same-named candidates has `suspend`) is E3050 regardless of the owner (variable, storage location, a temporary of the same expression). A borrow not used after the suspension point, and a borrow passed as an argument to a suspension-point call (alive only during the call), are out of scope. A function's reference parameter (the `p` of `fn t.b(p: &t.P)`) is also out of scope, and can be used across suspension points within that definition (the owner is on the caller side, and the caller guarantees it stays alive during the call). Local borrows are E3050 as before. This is a conservative rule, with room to loosen it later.
4. Execution is deterministic cooperative execution. Switching is round-robin in task id order. At a suspension point, from the next id on, a runnable task, or a task whose awaited counterpart has finished, is chosen. The body of `block_on` is id 0. The implementation is the tree walker (`src/task.rs`), creating one OS thread per task and passing a "only one may run now" signal. Only the thread that holds the signal touches the interpreter, so values are not shared (the `Send` requirement is satisfied by the executor running only one at a time. In stage 1, `Send` is not required of the executor).
5. Executor boundary: the effect of `block_on` is `E` (the effects of `f`), and when instantiated becomes the effects of the body of `f`. The caller declares `E`, so `suspend` is required only when `f` suspends (when `suspend` enters `E`), and it is not required if a non-suspending `f` is passed (E4001 stays the existing effect rule. The implementation is exactly this). A special rule only for `block_on` (a form that subtracts `suspend` from `E`) is not made.
6. Native (KIR / LLVM) is not lowered in stage 1 (`ksn build --release` fails with E9040, and does not fall back). It is lowered in stage 2 (0.10.18) (see "Implementation status" above). A debug build becomes the bundled bundle (interpreter). `ksn run --engine=tree` can select the tree walker (the default is the VM).
7. There is no cancellation (task discarding / canceling) (`Task<T>.cancel` was added in stage 4 (0.10.28). See "Decision (stage 4)" below). It is checked that a cancellable frame holds no value requiring release (E4022), so no obligation is lost during suspension and the rules for linear values do not change.
8. The form of passing `suspend` to the `E` of `dyn Tr<E, P>` (open point (8)) is expected to follow the rules of 5.1, but the check was not tried in stage 1 (not in tests).

Points carried over to stage 2 and later: (a) the native executor (tasks on top of real threads) and the implementation method of suspension (state machine or separate stacks), (b) the `Send` requirement on the executor, (c) the rule for stopping suspension at the executor's boundary (subtracting from the `E` of `block_on`), (d) how to write the effect arguments of `Fn*` bounds (waiting for the result of 4-6), (e) `suspend` versions of `std.net` / `std.fs` (select by type, or separate versions), (f) cancellation, and whether to make `Task<T>` linear, (g) loosening borrows across suspension (borrows of arguments, handling on WASM), (h) checking suspension through `dyn`.

#### Decision (stage 3, 0.10.21)

Of the carry-overs above, the following were decided. (a) (b) (c) (e) (g) remain for stage 4.

1. Suspension of `Result` (E9040 of stage 2): implemented. Suspending functions that return `Result`, and forms that hold a `Result` as a value spanning suspension (including the types of the results of `block_on` / `spawn_local`), give the same result natively as in the tree walker. Within a frame, a `Result` is placed split into a tag (1 byte, 1 for Err) and two payload fields for Ok and Err. Reading and writing are done with the helper functions `ksn.res.put<T>` / `ksn.res.get<T>` that the conversion makes per type, branching on the tag and reading or writing only one field. A form that uses `?` inside a suspending function (making the call `t.step(n)?` a suspension point) also gives the same result in the tree walker and native. What remains as E9040 is only forms where the wrapper's aggregate has a `Result` field, such as `Option<Result<..>>`, and types that cannot be put in a frame.
2. Cancellation (f): not included in stage 3. A mechanism is needed to clean up, at each suspension point, owned values (`Vec`, etc.) in the frame of a canceled task. In addition, a rule that guarantees by checking the condition for being cancellable (no linear values in the frame) and a decision on whether to make `Task<T>` linear are needed. `Task<T>.cancel()` is not exposed in the API. These are decided together in stage 4.
3. Suspension through `dyn` (h): the check follows the existing rule and is judged by the `uses` of the trait's method (if the method beyond the `dyn` has `suspend`, the caller is required to have `suspend`). It was confirmed that in the tree walker, a form that calls a suspending method through `dyn` from inside `block_on` works, and that calling it from a function that does not declare `suspend` gives E4001. Native stays under the existing restriction (E9040. Not specific to suspension) that a function taking `dyn` as an argument is not lowered to KIR.
4. `Fn*` bounds (d): a form in which `suspend` enters the effect argument `E` (passing a suspending closure to `fn t.apply[F: core.ops.FnOnce<(), u32, E, P>, E: uses, P: panics](f: F) -> u32 uses [E]`) can run inside `block_on`, and gives E4001 in a caller that does not declare it. The grammar for omitting effect arguments in 4-6 is unchanged.
5. Suspension waiting on a JS Promise in wasm32 (the requirement of 4. The form of `std.task.await_js`): sent to stage 4. Only the policy is decided. Waiting for JS completion can be done only outside the executor, so the executor returns "all tasks are waiting for JS completion" as a return value, and the caller of `block_on` is included in the state machine as a suspension point. For that, a "wait" is added to the return value of `ksn_main`, and an ABI is introduced in which JS calls a resume export after completion. The existing event-driven SPA (`apps/todo_spa`, the form of `ksn_fetch_done`) is not changed. No node test was made in this stage.
