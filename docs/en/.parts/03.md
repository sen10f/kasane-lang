## 4. Types and memory

### 4.1 Basics

- Borrow checking follows Rust 2021-equivalent NLL (including two-phase borrows, reborrowing, and partial moves). Lifetime declarations are placed at the head of the type-parameter list: `fn app.util.pick['a, T](x: &'a T, y: &T) -> &'a T uses [] panics never`. They can be omitted in only two cases: (a) the return value's reference has exactly one reference argument, and (b) the first parameter is `self: &...` / `&mut ...` and the return value's reference derives from `self`. When (a) or (b) applies, omission is the canonical form, and writing it explicitly is E3021. In every other case it must be explicit in the header. The default lifetime of `dyn` cannot be omitted (`'static` is also written explicitly). References (and types containing references) cannot be placed in the fields of `type` / `enum` or in variant payloads (references are second-class values. See "references are second-class values" below, E3060. Only `&'static T` has no region, so it can be placed). Type paths in input position of a header (such as `&mut core.fmt.Formatter`) may omit all lifetime arguments, and each is regarded as an independent fresh lifetime (explicit is required in output position). A lifetime argument that appears only once in input position is canonically omitted (if the output is also omitted, the input is also omitted: `fn app.u.get(p: &app.u.P) -> &str`), and declaring and writing it explicitly is E3021 (when it also appears in the output, or appears two or more times in input position and ties the inputs together (`fn app.util.keep['a](slot: &mut Option<&'a T>, x: &'a T) -> ()`), it is declared and written explicitly. The borrow of the tied input moves, at the call site, to the receiver of the `&mut`). This elision rule applies only to `fn` headers, and the lifetime arguments of the target type of an `impl` line are not omitted but declared and explicit with `impl['a, ..]`. The `&T` in the argument tuple of an `Fn*` bound (`core.ops.Fn<(&T,), bool, E, P>`) is regarded as taking an arbitrary lifetime per call. The rule for regions of omitted inputs (E3010): a reference omitted in input position of a header (`x: &T`, `x: Option<&T>`, the inside of `x: & &T`, etc.) has a fresh region per call, unrelated to the others. The borrow of this region (1) flows to an omitted output reference only when there is exactly one input reference (or, for `&self`, the region of `self`). (2) It does not flow to an output with a named lifetime or `'static` in any form: returning, wrapping in `Some` / a tuple / a struct, dereferencing (`*x`), extracting by `match` / `if let` / `for` / destructuring, or returning via a closure. (3) It also cannot be stored into the pointee of another input (a field, element, or `*out` of a `&mut` argument) without sharing a named lifetime. The pairs of storage and forwarding are determined only by the region relations in the callee's header (lifetimes of the same name, shared type parameters). When a region cannot be read (cannot be determined), the borrow is treated as flowing (the safe side).
- References are second-class values (0.11. E3060). Types that carry references (`&T` / `&mut T` (except `'static`), the standard types that take lifetime arguments `core.slice.Iter<'a, T>` `core.str.Chars<'a>` `core.str.Split<'a, 'b>` `alloc.collections.HashMapIter<'a, K, V>` `std.sync.MutexGuard<'a, T>`, `Option` / `Result` / tuples / arrays / slices containing them, and closures that captured references) can be placed only in parameters, return values, and local bindings. The following are E3060: (1) placing a lifetime argument in a `type` / `enum` declaration (`type app.v.View['a]`), or a field or variant-payload type that carries references (`Option<&T>` too). (2) Putting a reference-carrying type in the type arguments of the standard container, sharing, and send/receive types (`alloc.vec.Vec` `alloc.collections.*` `alloc.boxed.Box` `alloc.rc.*` `alloc.raw.Buf` `alloc.arena.Arena` `alloc.arena.Handle` `alloc.arena.Slot` `std.sync.*` (`Arc` `Mutex` `RwLock` `Sender` `Receiver`, etc.) `std.thread.JoinHandle` `std.task.Task`) and in the type arguments of the user's generic `type` / `enum` (all of headers, `let` annotations, explicit type arguments in expressions, and inferred types. `Vec<&'a T>` is also not allowed). (3) Putting a closure that captured references (`capture [&x]` / `[&mut x]`, `move` of a reference value) into a field, container, or channel, or `spawn`ing it. (4) Placing a reference-carrying type in a trait type argument on an `impl` line (`impl core.iter.Iterator<&u64, ..> for X` is E3060). `&'static T` (a reference with `'static` written explicitly) has no region, so it is an exception, and may be placed in fields and container type arguments (for a container type argument inferred as a reference, it is regarded as `'static` only when it can be shown that only string literals are put in; otherwise an annotation `Vec<&'static str, A>` or an owned value is required). Standard types that take a lifetime as an argument (`core.slice.Iter<'a, T>`, etc.) are also an exception. What is permitted: receiving references as arguments, returning them (tying to arguments by the elision rules or `['a]`), holding references, `Option<&T>`, `Result<&T, E>`, and tuples in local variables, and putting a reference in the type argument of a generic function (`t.id(&x)`). A structure that holds references (such as a parser pointing into its input string) should be written in the form of holding a position index and passing the original data as an argument.
- There is no null, no exceptions, and no implicit type conversion. There is no shadowing either: declaring, within a function (including closure bodies), a name equal to a binding, parameter, or trailing name of an imported module that is visible at that point is an error (the same name in sibling scopes that cannot see each other is permitted).
- Variables are initialized at declaration. Mutability is explicit with `mut`.
- Heap allocation specifies the allocator explicitly as an argument or in the type, and allocation always returns a `Result` (allocation failure does not panic). Allocation is the side effect `alloc`; deallocation is not a side effect (5.1).
- Integers have the operators `+ - * / %` and unary `-`. Both operands are of the same integer type, and overflow, division by zero, and sign negation of an unsigned type panic (accompanied by `panics may`. They cannot be used in a `panics never` function: E4004). To choose the behavior, use methods of the forms `a.checked_add(b)` / `a.wrapping_add(b)` / `a.saturating_add(b)` (`checked_*` returns `Option`; `wrapping_*` / `saturating_*` return a value). The negation methods are `checked_neg` / `wrapping_neg` / `saturating_neg`. Division truncates toward 0. Signed `MIN / -1` and `MIN % -1` overflow (panic. `checked_div` / `checked_rem` give `None`). Comparison and bit operations (`& | ^ !`) can be written with operators. Shifts are the methods `checked_shl` / `wrapping_shl` / `checked_shr` / `wrapping_shr`; `checked_` gives `None` if the amount is at least the type width, and `wrapping_` applies the amount modulo the type width. Floating point has `+ - * /` and unary `-` (no panic) (there is no `%`, only a `rem` method).
- The targets of indexing `a[i]` are only arrays `[T; N]` and slices `[T]` (the index is `usize`). Indexing panics when out of range, so it is accompanied by `panics may`. Where `panics never` is needed, use `a.get(i)` (returns `Option`). There is no range syntax `..`; use `core.iter.range(a, b)` (half-open interval) and `a.sub(i, j)` (`Option<&[T]>`).
- The arms of `match` are separated by newlines, and no `,` is attached at the end of an arm. A `,` at the end of an arm is E0049 (`ksn fmt` removes it in the same way as `ksn fix`. A `,` at the end of a `=> {` block whose arm body spans multiple lines, or at the end of call arguments, is also regarded as the end of an arm. `,` inside argument lists, tuples, and arrays is unrelated).
- `match` must be exhaustive. `_` can be used only for scrutinees of integer types, `char`, `&str`, and floating point. `_` and binding-only arms (`x => ..`) cannot be used for `enum` and `bool` (E2021), and all variants are enumerated. The exhaustiveness check also decomposes nested patterns (`Some(None)`, literals in variant payloads, tuples) column by column, and a `match` of only integer, `char`, or `&str` literals is not exhaustive unless it has a `_` or binding arm (E2021). An arm that is unreachable because earlier arms cover it (an arm after `_`, a duplicate of the same pattern) is E2052.
- To look at only one shape, use `if let` and `is` (syntax to keep `_` unusable for `enum` while not changing the enforcement of full enumeration in `match`).
  - `if let pattern = expr { .. } [else { .. } | else if ..]` is checked and executed by the same rules as `match expr { pattern => { .. }, everything_else => else side }` (omitting `else` makes the `else` side the empty block `()`). The types, borrows, and moves of names bound by the pattern are the same as one arm of `match`, and are visible only inside `then`. The "everything else" arm is created by the syntax, so it is not E2021 even for `enum` / `bool`. If the scrutinee is a linear value (or contains a linear value in a part that the pattern does not extract), the value is discarded on the `else` side (the implicit empty `else` if there is no `else`), and as with `_` in `match` this is E3003.
  - `expr is pattern` returns `bool`. It is the same as `match expr { pattern => true, everything_else => false }`. The pattern cannot bind names (use `_` for parts you want to bind. Syntax error E0002). Its precedence is non-associative, the same as the comparison operators, and you write `a is P && b is Q` and `!(a is P)`. `is` is a contextual keyword and can also be a variable name. A part of a linear value received with `_` is E3003, the same as in `match`.
- When `?` is used on an expression of `Result<T, E1>` in a function (closure) returning `Result<U, E2>`: (a) if `E1` and `E2` are the same type, it is returned as is; (b) if different, only when `E2` is an `enum` that declares `derive [From]` (4.3) and has exactly one variant `V` whose payload is exactly one and whose type matches `E1`, the error is wrapped as `E2.V(err)` and returned. Otherwise it is E2020 (the diagnostic shows both "add `V(E1)` to an `enum` with `derive [From]`" and "write `map_err`"). When two or more variants carry `E1`, it is E2049 (the diagnostic lists the variant names. Ambiguity is not silently resolved). The conversion is only one step (it looks up only a variant that directly carries `E1`. There is no chaining, reverse direction, or identity conversion, and an `enum` with type arguments is also out of scope). Free conversions such as keeping only part of `E1` or combining several `E1`s into one variant are written by the caller or a helper function with `map_err`. The return type of `?` inside a closure is that closure's return type. `?` on `Option` has no conversion and can be used only on `Option` in a function that returns `Option`. Only a variant construction is wrapped, so the effects and panics of `?` do not change.

### 4.2 Permitted implicit behaviors (there are none besides these)

| Behavior | Condition |
| --- | --- |
| Automatic call of Drop | At scope end, in reverse order of declaration (fields in declaration order, temporaries at the end of the statement). After a conditional move, controlled by a run-time flag, and moved-from values are not dropped. Drop is limited to `uses [] panics never` (4.4) |
| Running cleanup (`with`) | Only the `close` expression of a `with` expression (4.4). On every path that leaves the body (tail, `return`, `?`, `break`, `continue`), it runs exactly once after the exit value is determined and before control leaves. It does not run on panic or `std.process.exit` (5.2). It is a control construct at the written position, and separate from the implicit `Drop` |
| Auto-dereference and auto-reference | Only for the receiver of a method call (`&` / `&mut` is supplied to match the type of `self`) |
| Copy | Only for types that implement `Copy`. Everything else moves |
| Reference weakening and reborrowing | `&mut T` → `&T`, and reborrowing |
| Never-type conversion | From `!` to any type |
| Effect subtyping | Only conversion of function values and `dyn` by the subtyping relation of `uses` / `panics` in 5.1, and covariance of the effect arguments of trait bounds (4.3) |
| Conversion to `dyn` and function pointers | `&T` → `&dyn Tr + 'a`, `&mut T` → `&mut dyn Tr + 'a`, and their composition with reference weakening (`&mut T` → `&dyn Tr + 'a`) (`T: Tr`, `Tr` is dyn-safe, `T: 'a`). Function / closure without captures → the corresponding `fn(..)` type. `alloc.boxed.Box<T, A>` → `Box<dyn ..>` is not implicit but explicit with `alloc.boxed.Box.into_dyn` (5.1) |
| Array → slice | `&[T; N]` → `&[T]`, `&mut [T; N]` → `&mut [T]`, and their composition with reference weakening (`&mut [T; N]` → `&[T]`). Only directly under a reference; conversion inside a container such as `Option<&[T; N]>` is not allowed |
| Error conversion of `?` | When a function (closure) using `?` on `Result<T, E1>` returns `Result<U, E2>`, `E1` ≠ `E2`, `E2` is an `enum` with `derive [From]`, and there is exactly one variant `V` whose only payload is `E1`, the error is wrapped as `E2.V(err)` (4.1). One step only. `Option` and `E1` = `E2` are out of scope |
| Automatic implementation | `core.ops.Fn*` (4.3), `core.marker.Send` / `Sync` (5.5), and built-in implementations: integers, `bool`, and `char` have `Clone` / `Copy` / `PartialEq<Self>` / `Eq` / `PartialOrd<Self>` / `Ord` / `Hash` / `Debug` / `Display`; floating point has the same set except `Eq` / `Ord` / `Hash`. `&T` is `Copy` + `Clone` (`&mut T` is neither). `()`, tuples, `[T; N]`, `&[T]`, and `&str` have `Clone` / `Copy` (when all elements are `Copy`) / `PartialEq<Self>` / `Eq` / `PartialOrd<Self>` / `Ord` / `Hash` / `Debug` when their components implement them (`&[T]` and `&str` are references, so `Clone` / `Copy` always hold). `fn(T) -> U uses [E] panics P` implements `Fn<(T,), U, E, P>` and its supertraits (`FnMut` / `FnOnce`). `&T` / `&mut T` forward-implement `PartialEq<Self>` / `Eq` / `PartialOrd<Self>` / `Ord` / `Hash` / `Debug` when `T` implements them. Built-in implementations are outside the orphan rule (3.2) |
| Prelude | Only `Option` `Some` `None` `Result` `Ok` `Err` and the primitive types (4.5). Usable without name resolution. Writing them bare is the canonical form, and writing them in FQN form such as `core.option.Option` in types and patterns is E1110 (the method FQN `core.option.Option.map` is as before). `import core.option` is allowed only when using other items. Prelude names take precedence over "the same module is by FQN" in 3.3 (inside `core.option` / `core.result` too, `Option` / `Some` are written bare) |

The number of reference levels in type arguments, tuple elements, and the contents of `Option` / `Result` is not adjusted implicitly (`&u32` and `u32` are different types. Compare with `Some(&x)`, or write `match o { Some(x) => Some(*x), None => None }`).

The operands of operators (arithmetic, bit, comparison, unary) also do not have references stripped. A pair with different numbers of reference levels is E2024 (for `c: &u8`, `*c == b' '` rather than `c == b' '`, and for `o: &Foo`, `*o == f`). References with the same number of levels (`&str == &str`, `&Foo == &Foo`) pass as comparisons through the forwarding implementation of `&T` (the automatic implementation of 4.2).

### 4.3 Type system

- Type inference is only within functions. Headers require type annotations everywhere.
- Generics are monomorphized. Traits are implemented only explicitly with `impl` (no inheritance, specialization, or overloading). Bounds on type parameters are written in the header as `[T: A + B]` (there is no `where`). A trait's supertraits are declared with `requires` in the header: `trait core.cmp.Ord requires core.cmp.Eq, core.cmp.PartialOrd<Self> pub`. When `T: Ord`, `T: Eq` also holds. In the bounds and `requires` of traits that have type parameters, all arguments are stated explicitly (`T: core.cmp.PartialEq<T>`).
- Effect variables and panic variables state their kind in the type-parameter list: `E: uses`, `P: panics`. Actual arguments are a `uses` set (`[io.fs, time]`) and `never` / `may`. `uses [alloc, E]` is the union of sets. The order of elements is fixed: in `uses`, concrete names in UTF-8 byte order, effect variables at the end. `derive` is in the order listed in 4.3. `requires` and `+` bounds are in FQN byte order, with `linear` first and lifetime bounds last. Listing elements in an inclusion relation (`io` and `io.fs`) or duplicates in `uses` is E0021. `capture` is in identifier order. The type-parameter list is in declaration order. Constant parameters are `[T, const N: usize]` (`N` is an integer type / `bool` / `char`). The actual argument is a literal or a `const` name: `app.arr.Buf<u8, 16>`.
- Declarations are `[...]`, application of types and traits is `<...>`, and explicit type arguments in expressions are `f::<T, U, [io.fs], never>(x)`.
- Comparison operators: `==` `!=` correspond to `core.cmp.PartialEq`, and `<` etc. to `core.cmp.PartialOrd`. `PartialEq` / `PartialOrd` take the type of the right-hand side as a type parameter (`a == b` is `A: PartialEq<B>`), and derive generates the `<Self>` implementation. `Eq` `requires` `PartialEq<Self>`, `Ord` `requires` `Eq` and `PartialOrd<Self>`, and `Hash` `requires` `Eq`. `!=` is the negation of `eq`, and `<` etc. are derived from `partial_cmp` (there are no default implementations, so the traits have only `eq` and `partial_cmp`). `f32` / `f64` implement only `Partial*`, and do not implement `Eq` / `Ord` / `Hash`. There is no user-defined operator overloading (only the `Partial*` of comparison).
- Boilerplate implementations are written with the built-in `derive [Debug, Clone, Copy, TryClone, Drop, PartialEq, Eq, PartialOrd, Ord, Hash, From, ToJson, FromJson]` on the `type` / `enum` header (`From` is `enum` only). `TryClone` generates an implementation of the trait `alloc.alloc.TryClone` (8.3), calling `try_clone` for each field (payload) and propagating with `?`. If not all fields are `TryClone`, it is E2036 (a type that implements `Clone` also has `TryClone`, so primitive types, `Clone` types, and `alloc.vec.Vec<T, A>` (`T: TryClone`) can be included). The treatment of `linear` types is the same as for `Clone` (`TryClone` also cannot be derived). `Drop` has the implementation generate the destruction of recursive types (5.3). It provides an implementation of the trait `core.ops.Drop` and satisfies E4013 (the explicit-`Drop` requirement for recursive types). The target is a `type` / `enum` (may have type parameters) that has one or more recursions into `Self` with its own type parameters passed as is (polymorphic recursion is not allowed), and whose occurrences are only `Box<Self, A>` (an `enum` payload or `type` field) or `Option<Box<Self, A>>`. Anything else is E2051 (recursion through `Vec<Self>`, tuples, references, etc., mutual recursion with another type, use together with deriving `Copy`, use together with a hand-written `impl core.ops.Drop`), and a `linear` type is E2032 (same as `Clone` and `Copy`). Nothing is required of field types (owned things are destroyed as usual). The generated code destroys the whole tree with constant stack independent of depth (5.3). The generated implementation can be displayed in the same form as an ordinary definition with `ksn get --derived <FQN>`. `ToJson` / `FromJson` (`std.json` of 8.3) generate JSON input and output. `ToJson` generates an implementation of the trait `std.json.ToJson`, `to_json(self: &Self, out: &mut alloc.string.String<std.alloc.System>) -> Result<(), alloc.alloc.AllocError> uses [alloc] panics never`, and writes a struct as an object keyed by field names (in declaration order. `{"x":1,"y":2}`), and an enum as the string `"V"` for a variant without payload, `{"V":value}` for one payload, and `{"V":[value, ..]}` for two or more. `FromJson` generates an implementation of the marker trait without methods `std.json.FromJson` and an associated function `T.from_json(doc: &std.json.Doc, v: std.json.Value) -> Result<T, std.json.Error> uses [alloc] panics never` (a trait method requires `self` (3.2) and cannot be called statically from a type parameter, so decoding is an associated function per type, expanded from the field types. A struct ignores unknown keys, and a missing key is `MissingField` (an `Option` field also cannot be omitted, and `None` is `null`); an enum is an object with one key or a string). The types of fields (payloads) are limited to integers, `bool`, `alloc.string.String<std.alloc.System>`, `alloc.vec.Vec<T, std.alloc.System>`, `Option<T>`, and nominal types implementing the trait in question (`FromJson` cannot be derived for a type with type parameters. For hand-written decoding, write `impl std.json.FromJson for T` and `fn T.from_json`). Anything else (floating point, `char`, tuples, arrays, references, `Result`, nominal types that do not implement it) is E2036. The generated code is checked and executed as an ordinary definition, with line numbers starting from the line of the type (it is not built-in special treatment). There are no user-defined macros. `derive` is possible only when all of the `requires` of the trait to be generated are satisfied (`Copy` needs `Clone`). Bounds on type parameters are attached with "implements the trait in question" (`type app.coll.Vec[T] derive [Clone]` is `impl[T: Clone]`). The derive of `Ord` is lexicographic in field declaration order (for an `enum`, variant declaration order → payload lexicographic). A type that derives `Ord` has the provided methods `min` / `max` of `Ord` (`a.min(b)` / `a.max(b)` return `Self`. They follow `cmp`, and when equal `min` is `self` and `max` is `other`). `Copy` is possible only when all fields are `Copy`, and cannot implement `Drop`. `Clone` and `Copy` cannot be derived for a `linear` type. `From` is a marker that enables the error conversion of `?` (4.1) and generates no trait implementation. It can be written only on an `enum`, which has no type parameters and must have one or more variants whose payload is exactly one (`derive [From]` on a `type`, an `enum` without such a variant, or an `enum` with type parameters is E2050). The generated conversion is shown by `ksn get --derived <FQN>` as variants that wrap per payload type (if several variants carry the same type, it indicates ambiguity). The conditions for `Copy` / `Clone` apply to the payloads as they are (`derive [Copy, From]` is possible only when all payloads are `Copy`. An `enum` carrying `Copy` types such as `std.io.Error` or `alloc.alloc.AllocError` stays `Copy`).
- A closure expression is `fn(x: i32) -> i32 capture [&a, move b] { ... }` (`capture` comes right after the return type and cannot be omitted). A closure has its own anonymous type, and automatically implements those of `core.ops.Fn` (read-only. Can be called by shared borrow), `core.ops.FnMut` (mutates. Called by mutable borrow), and `core.ops.FnOnce` (consumes by move. Can be called once, by value) that hold, depending on how captures are used. The `uses` / `panics` of a closure are inferred from the body. Outer bindings referenced by the body must always be listed in `capture` (an omission is E1101). A captured `a` by `&a` / `&mut a` is written `a` in the body with type `&T` / `&mut T`, and `move a` is `T` (the same for `Copy` types. To use it as a value, write `*a`. Example: for `let k = 1u32`, `fn(n: u32) -> u32 capture [&k] { n.wrapping_add(*k) }`. `n.wrapping_add(k)` is E2023, and `total = k` in the body of `capture [&k, &mut total]` is E2024). Higher-order functions receive closures by bounds such as `[F: core.ops.Fn<(T,), U, E, P>]`. The function type `fn(T) -> U uses [E] panics P` is a function-pointer type with no environment, and only functions and closures without captures can be assigned to it. When `f`'s type satisfies `Fn*` in `f(a, b)`, it is desugared to `f.call((a, b))` (`call_mut` for `FnMut`, `call_once` for `FnOnce`), choosing the weakest bound that holds. A manual `impl` of `Fn*` is not allowed (E2034). The effect arguments of trait bounds and `impl`s are covariant: `impl Tr<.., E0, P0> for X` satisfies `X: Tr<.., E, P>` when `E0 ⊆ E` and `P0 ⊑ P` (`never ⊑ may`). When the same `E` / `P` appears in several bounds, it is resolved to the union of the actual arguments (`P` with `may` taking priority) (example: a closure with `uses [io.console]` can be `map`ped over an iterator source with `uses []`). The `Fn*` bounds of an `fn` header may omit both effect arguments `E` / `P` (`F: core.ops.Fn<(usize,), u8>`. Omitting only one is not allowed). An omitted bound is read as taking a fresh effect variable `E` and panic variable `P` only for that function (instantiated per call from the closure passed. 5.1), adding `E` to the function's `uses` and reading `panics never` as `panics P` (`panics may` stays as is). In other words, "it carries the effects of the closure passed, as they are". Example: `fn t.ap[F: core.ops.Fn<(usize,), u8>](f: F) -> u8 uses [] panics never` is the same as `fn t.ap[F: core.ops.Fn<(usize,), u8, E, P>, E: uses, P: panics](f: F) -> u8 uses [E] panics P`, and passing a closure with `uses [io.console]` makes the caller bear `io.console`, and passing a closure that may panic makes a `panics never` caller E4002. To restrict effects, state `[]` / `never` (or variables) explicitly as before (the check of explicit ones is unchanged). Only the bounds of an `fn` header can be omitted, at most one omitted bound per function, and it is also not allowed when `panics` is a variable other than `never` / `may` (all of these are E0002, asking for an explicit form). It cannot be omitted in the type arguments of `impl` / `trait` / `dyn`. `ksn fmt` and signature displays (hover / `ksn get`) output the omitted form as it is.

### 4.4 Drop and linear types

- Drop must be `uses [] panics never`. This keeps Drop from being a loophole for side effects and panics. `core.ops.Drop.drop` cannot be called directly, either by method call or FQN call (E3004. This prevents double drop). Destruction is only by `core.mem.drop(x)`.
- How `Drop` is called (implemented in KIR. `ksn run` / `ksn test` run a package that has a hand-written `Drop` not with the tree walker but with the VM (KIR bytecode), and if it cannot be lowered, they fail with a reason): when a value reaches the next point still alive (not moved), `drop` of that value is called once, and then the fields are destroyed in declaration order. The points are: the end of a binding's scope (in reverse order of declaration; for scopes left by `return` / `?` / `break` / `continue`, those scopes from the innermost), assignment to an initialized place (after evaluating the new value and before writing, the old value), `core.mem.drop(x)`, and temporaries at the end of a statement (the temporary of `let r = &expr` is at the end of `r`'s scope). An argument passed by value to a function is destroyed by the callee. A value of which only some fields were moved has only the remaining fields destroyed (moving a field of a `Drop` type itself is E3002). A value moved into the closure of `spawn` is destroyed in that thread. It is not called on panic or `std.process.exit`.
- A type whose destruction needs side effects (files, sockets, transactions) is declared `type ... linear`. Leaving a scope without consuming a value of a linear type is a compile error. It is checked on all paths, including early `return` and `?`.
- A type is linear if it is declared `linear`, or if it contains a linear value (field, variant payload, tuple element, array element, closure capture, type argument). Type parameters are non-linear by default, and to accept a linear type write `[T: linear]` (with `T: linear`, operations that need Drop cannot be used).
- The obligation of a linear value taken in by a closure with `move` moves to the closure, and the closure body must consume that value on all paths (the same check as for a linear binding inside the body. A path that does not consume is E3003). The closure itself also becomes linear, and is consumed by being called (or `spawn`ed). As an exception, `std.sync.Sender<T>` does not become linear even if `T` is linear (even if dropped, the owner of the values in the queue remains the receiver. 5.5).
- A value is consumed by passing it to a function that takes `self` by value, or by destructuring (`let app.net.Header { len: len, buf: buf } = self`. There is no shorthand for field names). `core.mem.drop(x)` can be called only when the type of `x` is non-linear. A `linear` type cannot implement `Drop`. A `Drop`-implementing type (hand-written or `derive [Drop]`) cannot be destructured by value with a pattern that binds fields (E3002).
- A `let`, `match`, or `if let` that destructures a linear value by value is always a consumption regardless of the pattern (even with only `_` or only `Copy` fields), and later use is E3002 (E3040 in the body of a `with`). To only peek inside, borrow and destructure as in `match &r { .. }` (a borrowed destructuring does not consume).
- Scoped cleanup `with name = initializer close cleanup_expr { body }` (an expression. The value is the value of the body block). Linear values (files, sockets) are not closed implicitly, and consumption is required even on the early `return` of `?`, so this is placed as syntax that makes consumption explicit at the place of use.
  - The `initializer` is evaluated first and bound to `name` (`with mut name = ..` for mutable. Patterns cannot be used, only a simple identifier). When the initializer exits via `?` etc., nothing has been bound and the cleanup does not run. `close` is a contextual keyword meaningful only at the position of `with` (it can be used for names of methods, variables, and fields).
  - The `cleanup_expr` runs exactly once on every path that leaves the body (tail, `return`, `?`, `break` / `continue`), after the exit value (the value of `return`, the `Err` returned by `?`, the value of the block) is determined and before control leaves. Nested `with`s clean up from the inside out. It does not run on panic (5.2) or `std.process.exit`. The `uses` / panics of the cleanup expression are counted as those of the enclosing function's body.
  - The `cleanup_expr` must consume `name` as a value exactly (`core.mem.drop(s.close())`, etc. Consuming only inside an `if` / `match` / loop is not allowed. E3041), and its type must be `()` (values are not silently discarded, so a `close` that returns a `Result` is handled with `core.mem.drop(..)` or `match`. E2045). `return` / `break` / `continue` / `?` cannot be written (E3042). When the failure of `close` must be returned to the caller, do not use `with` and handle the result by hand.
  - In the body, `name` can be used by borrowing (methods taking `&self` / `&mut self`. Use `with mut` for `&mut`), but moving, consuming, and reassigning are not possible (the cleanup would use a moved-from value. E3040). The value of the body must not be a reference borrowed from `name` (E3043). `name` is visible only inside the `with`, and the shadowing rule (4.1) applies.
  - Writes and the failure of `close`: discarding the `Err` of `close` in the cleanup of a `with` is allowed only for resources whose `close` cannot lose data (files opened for reading, sockets after the exchange is complete). For a file being written, a failure to write out data can first appear at `close`, so end the body with `f.sync()?` (`f.flush()?` if durability is not needed) and return the write-out failure to the caller with `?`. After that, the cleanup `core.mem.drop(f.close())` may discard. `std.fs.File.sync` writes out the buffer and asks the OS to make it durable (`fsync` on POSIX, `FlushFileBuffers` on Windows). Example: `with mut f = std.fs.create(path)? close core.mem.drop(f.close()) { core.mem.drop(f.write(data)?)` followed on the next line by `f.sync()?`.
  - A linear `name` is consumed by the cleanup on every exit of the body, so it is not reported as a leak (outer linear values are as before).
  - Example: `let n = with mut f = std.fs.open(path)? close core.mem.drop(f.close()) { f.read(&mut buf)? }`

### 4.5 Primitive types

- Integers: `i8 i16 i32 i64 i128 isize u8 u16 u32 u64 u128 usize`. The widths of `usize` / `isize` depend on the target: x86_64 and aarch64 are 64-bit, wasm32 is 32-bit (decision 2026-11-14. This replaces the former "fixed at 64-bit on all targets"). `usize` and `isize` are types distinct from `u64` / `i64` and from the other integer types, and conversions between types are explicit with `try_from_*` / `from_*` (there is no `as`), so the width does not change implicitly when the target changes. Places where how a value overflows can change with the target are handled by checking as follows ((1) and (2) were implemented in 0.10.14, (3) in 0.10.30): (1) integer literals and `const` constant expressions bound to `usize` / `isize` types have their range checked at the width of the target of checking and building, and if they do not fit, it is the same out-of-range literal error as for other integer types (it passes on 64-bit targets, and targeting wasm32 makes a value exceeding 4294967295 an error for `usize`. No warning is created: 5.4). `ksn check --target wasm32-unknown-unknown` and `ksn build --target wasm32-unknown-unknown` perform the same check. (2) The failure of `try_from_*` and the overflow panic of `+ - *` on 32-bit targets follow the run-time rules (5.2), and static checks are not added. (3) The associated constants returning the maximum value and bit width of `usize` / `isize`, `core.num.usize.MAX` / `core.num.usize.BITS` / `core.num.isize.MAX` / `core.num.isize.BITS`, take the target's values. On 32-bit targets, the conversions that can lose values, `usize.from_u64`, `isize.from_i64`, and `isize.from_u32`, do not exist, and `try_from_*` (returning `Result`) is used instead (the normative signatures of 64-bit `core.num` are read with these three and the constant lines replaced only when the target of checking and building is wasm32).
- `f32` `f64` (IEEE 754), `bool`, `char` (a Unicode scalar value), the unit `()`, and the never type `!`.
- Compound: tuples `(A, B)`, arrays `[T; N]`, slices `&[T]` / `&mut [T]`, and string slices `&str` (UTF-8. `str` appears only in the form `&str`). Tuple elements are extracted only by destructuring `let (a, b) = t` (there is no `t.0`).
- The FQN of methods and associated functions of a primitive type `T` is `core.num.<T>.<name>` (e.g. `core.num.i32.checked_add`). `bool` / `char` are `core.bool.` / `core.char.`. The home modules of primitive types are `core.num` / `core.bool` / `core.char` (orphan rule of 3.2). Thanks to the prelude, bodies can write `i32.try_from_i64(x)` / `a.checked_add(b)`.
- There is no `as` cast. Integer ↔ integer is `try_from_*` / `from_*`, integer ↔ floating point is methods that state the rounding explicitly by name (`to_f64` / `trunc_to_i64`, etc.), and `char` ↔ `u32` is `char.try_from_u32` / `c.to_u32()`. All are provided by `core`.
- Static promotion of literals: references to literals and to arithmetic of only literals (`3i32 + 4i32`) (`&10u32` / `&(3i32 + 4i32)`) are placed in `'static` (the static region) in the initializers of `const` / `static`. `static X: &u32 = &10u32` passes just like `static X: &'static u32 = &10u32`, and the `'static` of a reference in the type of a `static` may be omitted (both the omitted and explicit forms are accepted). `let r: &'static u32 = &10u32` is also accepted. `&10u32` as a function's return value is not promoted, and even writing `-> &'static u32` is rejected with E3030.

### 4.6 Expressions and statements

- A statement ends at a newline, and there is no `;` (a `;` at the end of a line is rejected by `ksn check` with E0040, and `ksn fmt` / `ksn fix` remove it). Lexical rules: a newline does not end a statement on a line ending with `(` `[` `,`, or when the next line begins with `.`. The base line for wrapping is the physical line containing the opening bracket, argument and element lines are 4 spaces deeper than the base line, and the closing bracket is placed on a line by itself at the same depth as the base line (in nesting, the line of the inner opening bracket is the base line). Lines beginning with `.` of a method chain are 4 spaces deeper than the statement's first line and do not accumulate. A newline is always required right after `{` (there are no one-line blocks. The `{ ... }` in the example of 4.3 is an omission of the body). `return` `break` `continue` are expressions of type `!` and can be written in the arm of a `match` or the right side of a `let`. Wrapped arguments and array elements are one element per line, with `,` also attached to the last element (a trailing `,` is forbidden when not wrapped). Wrapping is done only when the line would exceed 100 characters (`ksn fmt` decides), and wrapping a statement that does not exceed is an error. A call that includes a block (closure, `if`, `match`) in its arguments always takes the wrapped one-element-per-line form. Comment lines (`//` and `///`) are exempt from newline suppression (even if the line ends with `,` or `(`, it is not joined with the next line). Parameter lists (headers, closures) are not wrapped. Struct literals and struct patterns are always written with one field per line (fields are separated by newlines and no `,` is written. `}` is placed at the start of a line at the same depth as the line where `{` was written, and `)` `?` `=>` etc. may follow after `}`): `let p = t.P {` / `    x: 1u32` / `    y: 2u32` / `}`. The old one-line form `t.P { x: 1u32, y: 2u32 }` and a `,` at the end of a field are fixed by `ksn fmt` (E0020. E0053 is abolished). A struct literal cannot be written directly as the leading expression of `if` / `while` / `match` / `for` (enclose it in parentheses).
- Comment lines can be placed only immediately before a definition at top level (before the `///`), and in bodies only as standalone lines at the same depth as statements. The only top-level exception is the module description at the start of a file (3.2. Separated by one blank line). The `}` of a block is placed at the same depth as the line containing `{`, and the inside is 4 spaces deeper. `ksn fmt` attaches a comment placed before a definition across a blank line directly before the next definition, closing the blank line (it moves together with the definition), and leaves comments after the last definition at the end of the file (the latter cannot be fixed, so it is reported as a violation as is). It never deletes comments.
- Inner blocks are `{ }`. Indentation is a format normalized by `ksn fmt` and carries no meaning.
- Control constructs: `if` / `else`, `if let` (4.1), `match`, `expr is pattern` (4.1), `loop`, `while`, `for x in <Iterator>`, `with` (4.4), `break` / `continue` / `return`. Blocks and `if` / `match` / `with` can return values as expressions. The heading line of `with` (from `with` to `{`) follows the same wrapping rules as other statements (wrapping of arguments, `.` lines of chains) and is subject to the 100-character line-length limit. A continuation such as `)? close g(` or `) {` may be written on the line of the closing bracket.
- If the last statement of a block is an expression, its value becomes the value of the block. The value of the last expression of a function body is the return value, and `return` at tail position (the last expression of the body of a function or closure, a branch of an `if` with `else`, an arm of a `match`) is forbidden (`ksn fmt` extracts the value and fixes it, and `check` gives E0020. A `return` without a value is `()`). `while true {` is also forbidden (`ksn fmt` rewrites it to `loop {`). An expression statement that discards a value other than `()` is an error. To discard a value, use `core.mem.drop(x)`. An `if` without `else` placed as a middle statement discards the value of its then branch (the value of the tail expression), so if the type of the then branch is other than `()` / `!`, it is E2042 (make it a `return` or state it explicitly with `core.mem.drop(x)`). The value of a block, `unsafe`, or `with` in a middle statement is likewise E2042. The value at the tail of the body of `while` / `loop` / `for` is also discarded, so other than `()` / `!` is E2042 (`break` takes no value). The values of statements that are `if` with `else` or `match`, and of calls to functions and methods (including `std.io.print_line(..)` and `v.push(x)`, which return `Result`), are also E2042 if other than `()` / `!`. The basic way for `Result` is to propagate it with `?` (`v.push(x)?`), and to discard it use `core.mem.drop(..)`. `let _x = ..` and the tail expression of a block are exempt.
- Assignment is a statement, not an expression: `<place> = <expr>`. A place is a `let mut` binding, `*r`, a field chain `a.b`, or an index `a[i]` (`panics may`). There is no compound assignment (`+=`, etc.).
- `let pattern[: Type] = expr` (mutable is `let mut x = ...`, and `mut` inside patterns is not used). Destructuring by patterns can be used in `match` and `let`, and in `let` only irrefutable patterns.
- Operators from strongest: unary (`-`, `!` (logical negation for bool, bit inversion for integers), `&`, `&mut`, `*`), `*` `/` `%`, `+` `-`, `&`, `^`, `|`, comparison (`==` `!=` `<` `<=` `>` `>=`, non-associative), `&&`, `||`. The exact grammar is `spec/grammar.ebnf`. When two `&` follow each other, write `& &x` with a space (`&&` is the single token of logical AND).
- Intentionally unused variables and parameters get a name beginning with `_` (`_buf`). Using a name that begins with `_` is an error. A lone `_` can be used only as the wildcard of `match`. Discarding a value is only by `core.mem.drop(x)` (`let _ = e` is forbidden).
