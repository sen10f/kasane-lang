# Kasane Language Specification (Concise)

> **This is an English translation. The Japanese text, [日本語](../../Kasane%20簡易仕様書.md), is normative.** If the two differ, the Japanese text wins. Translation status: see the end of this file for any section not yet translated.

Version: 0.10.45 / 2026-11-26 (0.10.45 records, all together: the execution of hand-written `Drop` (4.4), making the VM the default execution engine of `ksn run` / `ksn test`, failure of `?` in a test body (3.2), `std.thread.spawn`'s `SpawnError<F>`, `[unsafe] native = true` for `[native]` (E9024), and re-checking by instantiating generic effects (E3050). A summary of earlier versions is in chapter 10.)

## 1. Purpose

A language that keeps Rust-style memory safety, with syntax that is easy to handle for AI and grep, and thorough strictness.

## 2. Design principles

1. No GC. Memory is managed by ownership and borrowing.
2. Strictness first. No implicit behavior is introduced other than what is listed in 4.2.
3. Every definition (including methods and tests) is placed at top level and can be extracted with grep/awk. For reference analysis, `ksn refs` is authoritative.
4. Compilation is sped up per function, and the cache is kept bounded. When speed and size conflict, speed wins.
5. There is exactly one way to write the same meaning. The output of `ksn fmt` is the only canonical form, and both `ksn fmt --check` and `ksn check` treat any source that differs from the output of `ksn fmt` by even one byte as an error (E0020. Variation is not silently accepted: so that differences in appearance with the same meaning cannot hide changes slipped into the diff of a dependency update). `ksn fmt` only rewrites; whether the rewritten result passes checking is judged separately.

## 3. Syntax

### 3.1 Shape of a definition

- One definition = one header line + body + explicit terminator. Definitions do not nest.
- The header starts at the beginning of a line and is complete on one line. Header lines are exempt from the line-length limit.
- The name in the header is an FQN. A mismatch between the FQN and the file path is an error (3.6). The canonical form of type and trait references inside a header is also the FQN (3.3. `check` accepts short forms and `fmt` rewrites them).
- The terminator is `end <FQN>`. It must have the same name as the header.
- Every line of the body must be indented (in units of four spaces). Blank lines are allowed, however (see below). A non-blank line that is not indented is an error.
- Raw newlines inside string literals are forbidden. The `\n` escape is required.
- Attributes at the end of the header are in a fixed order, and only those that apply are attached.
  - `fn`: `const` → `uses` → `panics` → `stack` → `depth` → `impls` → `pub`. `uses` and `panics` must always be stated explicitly on every function (write `uses [] panics never` too. Omission is E4020. `ksn fix` writes in the values computed from the body). The values must match the effects of the body exactly (5.1, E4025). `stack` is only for recursive `panics never` functions (5.3), `impls` is only for trait implementation methods, and `const` is only for compile-time-evaluable functions (`const fn`). The line of a `const fn` always begins with `fn`.
  - `type` / `enum`: `layout c` → `derive [...]` → `linear` → `pub`.
  - `trait`: `requires <FQN>[, ...]` → `pub`.
  - `const` / `static`: `pub` at the end.
  - `ksn fmt` fixes order violations. If `ksn fmt` brings the source to the canonical form and the result passes checking, `ksn check` does not report an error (`fmt --check` reports it as a diff).
- `pub` is placed at the end of the header (to keep greps such as `^fn ` working without moving the leading keyword). If omitted, the definition is visible only within the same module.
- There are only two visibility levels (omitted = within the same module, `pub` = all packages). Every type and trait appearing in the header of a `pub` definition must be `pub` (a violation is E1010). A `type` field is visible only within the module by default, and appending `pub` to the end of the field line makes it public (`size: usize pub`). The variants of an `enum` follow the visibility of the `enum`. Referring to a non-`pub` definition of another module (whether by FQN or by an `import`ed short form) is E1119 (a module of another package also counts as "another module"). The visibility of an `impls` method automatically follows the smaller of the visibilities of the trait and the type, and writing `pub` is an error.
- A blank line contains neither indentation nor whitespace. Blank lines inside a body are allowed (consecutive ones are not, and neither at the start nor at the end of a body).
- Blank lines at top level: `import` lines are placed consecutively with no blank lines between them. Exactly one blank line is placed between the `import` group and the first definition, and between definitions (`const` / `static` / `extern` each count as a definition of one line). When an `fn` follows an `impl` line directly, no blank line is put between them. The single blank line right after the module description at the start of a file (3.2) is outside the scope of this rule.
- The order within a file is `import` → `const` / `static` → `type` / `enum` / `trait` → `extern` → `impl` lines without methods (`Eq`, `Copy`, hand-written `Send` / `Sync`, etc.; ordered by the string of the `impl` line, with one blank line between them) → `fn` (an `impl` line with methods goes right before its first `impls` method) → `test`. Within the same group, FQN order. Ordering comparisons are by UTF-8 byte sequence (uppercase before lowercase).

### 3.2 FQN and terminator per kind of definition

| Kind | Shape of the FQN | Terminator |
| --- | --- | --- |
| `fn` (function) | `app.net.parse_header` | `end app.net.parse_header` |
| `fn` (method) | `app.net.Header.len` (type FQN + name) | `end app.net.Header.len` |
| `type` / `enum` / `trait` | `app.net.Header` | `end app.net.Header` |
| `impl` | `impl core.cmp.Ord for app.net.Header` | none (one-line declaration, no body) |
| `test` | `app.net.parse_header.test_empty_input` (target FQN + a test name beginning with `test_`) | `end app.net.parse_header.test_empty_input` |
| `const` / `static` | `app.net.MAX_LEN` | complete on one line, no terminator |
| `extern` | `app.sys.getpid` | complete on one line, no terminator (3.8) |

When `?` in a test body returns Err / None, that test fails (the reason is `returned Err(<Debug display of the Err>)` / `returned None`. The `failure` of `ksn test --json` has the same wording. The same in the tree walker, the VM, and native `--both`).

- Modules, functions, types, methods, constants, and tests share a single FQN namespace, and duplicates (including a module and a definition with the same name) are E1103.
- Methods are not written inside an `impl`; they are placed as top-level `fn`s. If the first parameter is `self`, it can be called as a method.
- A method implementing a trait gets `impls <trait FQN>[<arguments>]` at the end of its header. A type can have only one method of a given name (even across traits). For this reason, the trait method names of the standard library are designed not to collide between traits (example: `core.fmt.Debug.debug_fmt` / `core.fmt.Display.display_fmt`).
- An `impl` line only expresses the correspondence table, and it is an error unless all methods of the trait are present with `impls`.
- Where an impl is placed (the orphan rule): the placement is always determined uniquely (the same (trait, type) is never placed in two places).
  - If the target type `T` is a nominal type (`type` / `enum`) of this package, the `impl` is placed in the module that defines `T`. If `T` is not of this package and the trait `Tr` is of this package, the `impl` is placed in the module that defines `Tr` (a type of the standard library such as `alloc.string.String` / `alloc.vec.Vec<T, A>`, or a primitive type such as `u32`, can also be given an implementation of your own trait, in the trait's module). If both are foreign (a standard-library trait for a standard-library type, etc.), it cannot be placed: E2043.
  - The FQN of a method on the type side is `<type FQN>.<method name>`, and on the trait side it is `<trait FQN>.<type FQN>.<method name>` (example: `app.json.ToJson.alloc.string.String.to_json`. It has the same shape as `<trait FQN>.<primitive type name>.<method name>` for primitive types, with the type FQN simply following). Placing the same (trait, type) on both the type side and the trait side is E1114.
  - An `impl` in a different place is E2043 (the message names the correct module). An impl of a trait of a dependency package, if it is in that trait's module, is found by method lookup (3) even if the user side has not `import`ed it.
  - When the target is a primitive type, the primitive type is foreign, so it is placed in the module that defines the trait. The method FQN is `<trait FQN>.<primitive type name>.<method name>`.
  - A bare type parameter (a blanket impl) can be placed only in the module that defines the trait, and the method FQN is `<trait FQN>.blanket.<method name>` (`blanket` is a reserved word).
  - An impl cannot be written for tuples (including `()`), `!`, references, slices, arrays, or function types (wrap them in a nominal type).
  - Only one impl is allowed for the same (trait name, type) even if the type arguments differ (because method FQNs must be unique. Example: `PartialEq<_>` for a type `T` is only one). There are no exceptions. Overlapping impls that can be unified, including type parameters, are also an error (there is no specialization).
- A method call `x.m(...)` looks up, for the type `R` of `x` (the type with references stripped), in this order: (1) `<FQN of R>.m`; (2) if `R` is a primitive type, `core.<num|bool|char>.<R>.m`; if `R` is a slice `[T]` (`&[T]` / `&mut [T]` strip the reference to `[T]`), `core.slice.m`; for `str`, `core.str.m`; for an array, `core.array.m` (tuples and unit have no methods. These modules are treated as the home modules of the respective types, following the orphan rule for primitive types); (3) methods of `impl`s targeting `R` (including the built-in implementations of 4.2. Methods of built-in implementations have no FQN, and `ksn get` returns the trait definition's signature) whose name is `m` (independent of `import`). For a type parameter `T: B`, only the methods of `B` and its supertraits. Multiple matches are E1108. An `fn` with `self` as its first parameter is an error unless its FQN is `<FQN of the type of self>.<name>`, or a trait-mediated form determined by the orphan rule above (including `<trait FQN>.<type FQN>.<name>`), or `core.slice.<name>` / `core.str.<name>` / `core.array.<name>` as determined by (2).
- A generic `impl` declares type parameters in the declaration: `impl[T: core.cmp.Ord] core.cmp.Ord for app.coll.Vec<T>`. The method in this case is `fn app.coll.Vec.cmp[T: core.cmp.Ord](self: &app.coll.Vec<T>, ...)`.
- Shapes of bodies (these are not "definitions" but declaration lines inside a body):
  - `type`: one or more field lines `name: Type [pub]`. A field name and a method name of that type (including trait implementations) cannot coincide (E1115. So that `ksn get <type FQN>.<name>` is unique) (zero lines is E0002. There are no tuple structs or unit structs). A type parameter need not be used in a field (it is outside the unused check of 5.4).
  - The body of a `type` / `enum` / `trait` (the sequence of declaration lines) cannot contain blank lines or comment lines.
  - `enum`: variant lines `Name` or `Name(Type, ...)`.
  - `trait`: only signature lines of required methods `fn name[generics](self: Self | &Self | &mut Self, ...) -> T uses [...] panics P` (`[generics]` may be omitted. The type of `self` is one of `Self` / `&Self` / `&mut Self`). There are no default implementations. A trait can have type parameters (`trait core.iter.Iterator[T, E: uses, P: panics]`), but there are no associated types.
  - Required methods, fields, and variants can be given as arguments of `ksn get` / `ksn refs` in the form `<definition FQN>.<name>` (a namespace separate from the FQN space of definitions. There is no `end`).
- A `test` header is `test <target FQN>.test_<name>`. If the target FQN does not exist, it is an error. A test is placed in the same file as its target and is excluded from release builds. A test body may use arbitrary side effects, and a panic means failure.
- Integration tests: `*.ksnl` files under `tests/` directly under the package (outside `src/`. The place for tests that span several modules).
  - Module: the module name of `tests/<name>.ksnl` is `<package name>.tests.<name>` (for subdirectories, `/` in the path becomes `.`). The module `<package name>.tests` and `<package name>.tests.*` are reserved for integration tests, and placing a module of the same name in `src/` is E1121 (3.6). Files in `tests/` are not part of the module tree of `src/` and cannot be referenced from other modules (they have only non-`pub` helper definitions).
  - Definitions allowed: `import`, `test`, and helper definitions used only by tests (`fn` / `type` / `enum` / `trait` / `impl` / `const` / `static`). `pub` cannot be attached to helper definitions, and `extern` cannot be placed (violations are E1120).
  - References: as with an external user, only `pub` definitions of the own package and of dependency packages. A non-`pub` reference is E1119 (3.1). Helper definitions in one's own file can be referenced.
  - Names: `test <module name>.test_<name>` (example `test shortener.tests.loopback.test_shorten_and_fetch`). The target FQN is the module of the test file itself, not an individual definition of `src/`. The rule "in the same file as the target" is thereby satisfied naturally, and since a test is not tied to a particular definition, there is no need to place a test under the name of an unrelated function (any form other than `<module name>.test_<name>` is E1116. Without the `test_` prefix it is E0010).
  - Tooling: `ksn test` runs the unit tests of `src/` and the integration tests of `tests/` (`--both` as well). They can be filtered by FQN prefix (`<package name>.tests` for integration tests only). `ksn check` / `ksn fmt` also cover `tests/`. The artifacts of a release build (`--release`) do not include `tests/`. It is not subject to the hash of 8.1, and the `tests/` of dependency packages is not loaded.
- A `///` documentation comment is placed on the line immediately before a definition header (or `const` / `static` / `extern`; excluding `impl` lines). When there is an `impl` line with methods, the order is `impl` line → `///` → `fn`.
- Module description: a block of `///` at the start of a file (before `import`) followed by exactly one blank line becomes the description of that file's module (at most one per file. It appears at the top of the page of a module that has public definitions. In `ksn index` it becomes the module's one line). A leading block without a blank line is the description of the definition right after it (it cannot be placed right before an `import`). A `///` block cut off by a blank line is an error (E0002) in any form other than this one.
- The body is a subset of Markdown: paragraphs (separated by blank lines), `` `code` ``, `**emphasis**`, bullet lists beginning with `- ` (one level), code fences (```` ``` ````. A fence whose info string is `ksn` is a code example; others are display only), and links `` [`FQN`] ``. Headings, tables, numbered lists, and HTML cannot be written and are output as plain characters (HTML is escaped).
- Links: `` [`FQN`] `` points to a definition (`fn` / `type` / `enum` / `trait` / `const` / `static` / `extern`) or a module. It resolves only when the FQN matches exactly, or when the trailing name is a short name unique among all loaded definitions (package, dependencies, standard library). One that does not resolve is E1125 (an error of `ksn check` and `ksn doc`). Fields, variants, tests, and `impl`s cannot be pointed to. When the link target is private, `ksn check` passes, and `ksn doc` outputs it as plain characters on public pages.
- Code examples: a fence whose info string is `ksn` is an example for a definition of `src/` (including the module description), and `ksn test` runs it (treated the same as an integration test in `tests/`. `ksn test --doc` runs only the examples). Only when the example body uses the name of that definition's module (the trailing name or an FQN prefix), the `import` of that module is attached automatically (an unused `import` would be E1020, so it is not attached otherwise). The content of the fence is written in the same way as a test body, with indentation starting at 0 (the tool indents it by 4). `fn main` is not needed, and top-level definitions cannot be written. Only public definitions are visible (same as a user). Output is not compared: what you want to verify is written with `core.check.eq` etc., and a failure is a panic. A syntax, type, or lint failure in an example appears as a failure of `ksn test`.
- The form of `const` / `static`: `const app.net.MAX_LEN: usize = 1_024 pub`. An initializer that cannot be written in one line is built with a `const fn` and called. A `const fn` is `uses []`, and the body can call only `const fn`s and compiler built-in methods (no `unsafe`, `extern`, or raw pointers). A panic during evaluation is a compile error (E4024), and the limit on evaluation steps is implementation-defined (this implementation: 10 million expression evaluations per initializer. Exceeding it is E4024). `static` is immutable only, and its type must be `core.marker.Sync` and non-linear (E2031) (mutable global state is expressed with atomic types of `core.sync` etc.).
