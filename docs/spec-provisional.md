## 1. モジュール

**現在の文言（引用）：**
> 1ファイル=1モジュール。既定は非公開、`pub` はヘッダ末尾（3.1）

**実装の現状：**
`ksn check` / `ksn run` で検証済み。1 ファイル＝1 モジュール（`mod` は廃止、行頭キーワードに `mod` なし）。定義ヘッダの末尾に `pub` を書くとそのモジュール外から参照可能になり、省略すると `E1119: ... is private to module ...` で拒否される（`secret.hidden` を他モジュールから呼ぼうとすると E1119、`pub` を付けると通る）。`import` は 1 行 1 モジュール、項目単位の import・別名は禁止。

**オーナー決定（AGENTS.md）：**
- 2026-11-26（S1c を置き換え）：公開するパッケージは `.ksnl` だけを持つ。依存の `.ksnh` は読まず E9050 の検査もしない。根のパッケージだけ E9050 を検査する。
- 2026-11-21（書き方は 1 通りを絶対に守る）：自モジュールの短縮名禁止など、モジュール解決・正規形は固定済み。

**未解決の問い：**
- モジュールをまたぐ相互再帰は「同一モジュール内のみ」と仕様にあるが、同じパッケージ内の異なるモジュール間での循環判定の境界が明確か。
- `pub` の伝播（ヘッダだけ `pub` で本体内部の参照が非公開の型を使う場合）の扱い。

**選択肢と帰結：**
- A. 今のまま「確定」とする（1 ファイル＝1 モジュール・既定非公開・`pub` ヘッダ末尾）。→ 実装と一致し、契約として安定。変更不要。
- B. `pub` をヘッダ先頭（`pub fn ...`）にも許可する。→ 文法変更が必要で `ksn fmt` / `check` の修正が走る。メリットは少ない。
- C. モジュール間の相互再帰を許可する。→ 循環検出・キャッシュキーの再設計が大きい。非推奨。

**推奨：** A. 実装と一致し、オーナー決定（`.ksnl` のみ公開等）とも整合する。「確定してよい」。

**判定：確定してよい**

## 2. エラー

**現在の文言（引用）：**
> `Result` と `?`（`derive [From]` の `enum` へ 1 段だけ包む）。例外なし

**実装の現状：**
`Result` と `?` は実装済み（デモ・ツール例で `fn ... -> Result<(), std.io.Error> uses [..] panics never` と `?` を使い、`ksn check` が通る）。`?` の終了コードは `Err` なら 1、panic なら 101。`derive [From]` による 1 段ラップのエラー変換は、現行の `ksn fix` 対象（E1020/E1108/E2041/E2042）には含まれていないようで、動作確認が必要。

**オーナー決定（AGENTS.md）：**
- 2026-11-25（pending_spec 10）：`std.thread.spawn` の失敗は閉包を返す（`Err(SpawnError<F>)`、署名変更）。エラー扱いの一環。
- 2026-11-25（pending_spec 8）：`panics never` はコードの panic の約束。デッドロック・資源枯渇・深さ上限（102）は約束の外。

**未解決の問い：**
- `derive [From]` の `enum` への「1 段だけ包む」が実際に動作するか（テスト未確認）。
- `?` でのエラー変換時に `E1` を運ぶバリアントが 2 つ以上ある `enum` の定義自体を許すか（使用時は E2049 で拒否。定義側制限は未記載）。

**選択肢と帰結：**
- A. 今のまま「確定」とする（`Result`/`?` は実装済み）。→ 契約として十分。`derive [From]` の詳細は `spec/stdlib` の `.sig` と実装で固める。
- B. 定義側で「`E1` を運ぶバリアントが 2 つ以上の `enum`」を制限する文を追加。→ 誤用の早期防止になるが、仕様・検査器の修正が必要。

**推奨：** A で「確定してよい」。B は別の改善Issueとして残す。

**判定：確定してよい**

## 3. 並行性

**現在の文言（引用）：**
> スレッド＋チャネルのみ。Send/Sync（5.5）。非同期はv1後に再検討

**実装の現状：**
スレッド（`std.thread.spawn` / `join`）・チャネル（`channel` / `send` / `recv`）・`Send`/`Sync` は実装済み。非同期は `async`/`await` の構文ではなく、効果 `suspend`（`uses [suspend]`）として導入済み（5.6）。`async`/`await` は予約語のまま、構文として導入しない（5.6、決定ログ 8）。`std.thread.spawn` の失敗は現在 `spawn failed: ...` の panic で止まり、`Err(SpawnError<F>)` を返すのは木走査（`--engine=tree`）だけ（ALPHA.md 既知の制限）。

**オーナー決定（AGENTS.md）：**
- 2026-11-20 夕方：非同期実行器の 2 段目はタスクを全スレッドで分け合う形（tokio 型、仕事の横取り。`Send` を求める）。
- 2026-11-24 夕方：`Send`/`Sync` の手動 `impl` は型を定義したモジュールだけ。標準の型への手書き `impl` は標準ライブラリの外では禁止。H5（総称の Send/Sync 境界を呼ぶ側で確かめない）はすぐ誤り。
- 2026-11-25（pending_spec 10）：`spawn` の失敗は `Err(SpawnError<F>)`。

**未解決の問い：**
- 「非同期はv1後に再検討」とあるが、`suspend` は既に実装済みで `std.task` / `block_on_threads` もある。v1 でどこまで非同期を取り込むか（`std.net`/`std.fs` の `suspend` 版等）。
- `spawn` の `Err(SpawnError<F>)` 移行は木走査・VM・ネイティブで一貫するか（現在は木走査のみ）。

**選択肢と帰結：**
- A. 「スレッド＋チャネル＋`suspend`（非 `async`/`await`）」で「確定」とする。→ 実装と一致。「非同期はv1後に再検討」は v1 以降の話として残す。
- B. `async`/`await` 構文を v1 で導入する。→ 文法・検査器・実行系の大きな変更。現行の `suspend` 効果と整合を取る必要あり。

**推奨：** A. 実装済みでオーナー決定とも整合する。「確定してよい」。

**判定：確定してよい**

## 4. FFI

**現在の文言（引用）：**
> C ABIのみ、`unsafe` 許可モジュール限定（3.8）

**実装の現状：**
`extern ... link "libm.so.6:cbrt"`（C ABI）は実装済み（`examples/ffi` で `ksn check` / `ksn run` が通る）。`unsafe` は `[unsafe] modules` に列挙したモジュール（`kasane.toml`）内の `unsafe "名前" "理由" { ... }` ブロックのみで、それ以外は E5001。`core`/`alloc`/`std` は暗黙に許可。

**オーナー決定（AGENTS.md）：**
- 2026-11-24 夕方：`unsafe impl`（`Send`/`Sync` 等）の書き方は作らず、一覧の道具（`ksn unsafe`）で補う。標準の型への手書き `impl` は標準ライブラリの外では禁止。
- 2026-11-25（pending_spec 12）：`[native]` を使うパッケージ（依存を含む）は `[unsafe]` の許可を求め、依存の `.a` は lock のハッシュに含める。

**未解決の問い：**
- 構造体の値渡しは「未対応」と仕様（ターゲット行）にあるが、FFI での構造体値渡しの扱いが明確か。
- `extern` の関数を値として扱うのは E5003 で拒否（決定ログ 19）。

**選択肢と帰結：**
- A. 今のまま「確定」とする（C ABI のみ、`unsafe` 許可モジュール限定）。→ 実装と一致。安全側。
- B. FFI を `unsafe` 許可モジュール以外でも許可する。→ 監査可能性が下がり、非推奨。

**推奨：** A。「確定してよい」。

## 9. 挙動一致

**現在の文言（引用）：**
> 固定幅整数、IEEE 754厳密（丸めはroundTiesToEven、FMA縮約・fast-math禁止、`f32` は `f32` 精度で演算）、評価順は左から右。NaNのビット列は、ビットが見える所（`to_bits`・FFIの引数）で単一のquiet NaNに正規化（演算ごと・メモリへの書き出しごとには行わない。見えない途中のペイロードは実装によらず保証しない。`unsafe` の生ポインタで浮動小数のメモリを整数やバイトとして読んだときのNaNのペイロードも保証しない）。標準HashMapの反復順は挿入順で、削除後も残りの相対順を保つ。一致保証はシングルスレッド・coreの数学関数の範囲で、ポインタの整数化は対象外

**実装の現状：**

- 2026-11-24 夕方：HashMap は挿入順を保つ。Fnv64 は変えない。
- 2026-11-24 夜：最優先は脆弱性への対応（性能・資源より上）。

**選択肢と帰結：**

## 11. ターゲット

**現在の文言（引用）：**
> `x86_64-linux-gnu` / `aarch64-linux-gnu` の Linux と `x86_64-windows-gnu`（MinGW-w64。組み込みの lld でつなぐ。crt・import ライブラリは `/usr/x86_64-w64-mingw32`、`KSN_SYSROOT` で上書き）を `ksn build --target` で対象にできる（LLVM）。Windows の `extern` は `link "lib.dll:名前"` を `LoadLibraryA` で引く。std.process は `CreateProcessW` で動く（シグナルはなく `signal` は常に 0）。構造体の値渡しは未対応。macOS は未対応（クロスコンパイルの対象外は E9040）。WASM は未着手

**実装の現状：**
`ksn build --target x86_64-linux-gnu / aarch64-linux-gnu / x86_64-windows-gnu` は LLVM でネイティブ生成。`wasm32-unknown-unknown` / `wasm32-wasi` も対応（7.2 WASM ABI、WASI の関数一覧）。macOS は未対応。構造体の値渡しは未対応。WASM の SPA は実験的（Edition 1 範囲外）。
