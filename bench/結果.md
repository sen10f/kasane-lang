# ベンチ結果（Kasane、資料の有無と診断の質）

モデル: Claude Haiku（思考量は最低）のサブエージェント 11 本。課題は `bench/tasks.py` の 11 本。
評価は `bench/eval_files.py`（`ksn check` と、評価側が追記した `test`）。書き直しは、診断だけを返して最大 3 回。
Gemma 12B（LM Studio）での実測は、1 回の生成に 5 分以上かかったため、一部（gcd・fib・is_prime）で中断している。

## 結果（累積の合格数 / 11）

| 条件 | 最初 | 書き直し 1 | 書き直し 2 | 書き直し 3 |
| --- | --- | --- | --- | --- |
| 資料あり（チートシート + 動く例） | 11 | - | - | - |
| 資料なし、診断は 1 件ずつ | 0 | 0 | 3 | 5 |
| 資料なし、診断をまとめて直し方つき | 0 | 1 | 8 | 8 |

その後、診断をさらに改善して（E0047 type/enum の括弧形式、E0048 構造体リテラルの括弧、E0049 アーム末尾のカンマ、E1101 の近い名前の提案、課題文の宣言を中立な記述に変更）、残っていた shape・counter・sum_squares を書き直し 4 回目に渡したところ、3 本とも合格した（累積 11/11）。この 3 本は、前の 3 ラウンドの履歴を引き継いだエージェントで測っている。

最後の条件は、途中で診断（E0043 の文、E0046）を改良しながら測っているため、厳密な条件比較ではない。

## 分かったこと

- 資料の効果は大きい（11/11 と 0/11）。「Rust に似た言語」とだけ伝えると、モデルは Rust で書く（波括弧、`;`、`::`、`as`）。
- 診断をまとめて直し方つきで出すと、資料なしでも 8/11 まで書き直しで到達する。
- 診断の文は、直す範囲と残す範囲を両方書く必要がある（`while` の波括弧まで消された）。
- 通らなかった 3 本（shape・counter・sum_squares）の原因:
  - 課題文の宣言が `enum X (A(i32), ...)` のような略記だった。ベンチ側の誤誘導。
  - `type` / `enum` の本体の書き方（インデントした行）に診断が触れていない（E0002 が出るだけ）。
  - `core.vec.Vec.new` のような存在しない名前に、近い名前の提案が出ない（`alloc.vec.Vec.new`）。

## 次の改善候補

1. `type` / `enum` の 1 行（括弧）形式を検出し、「フィールド・バリアントは 1 行ずつインデントして書く」と指摘する。
2. 存在しない名前（E1101）に、近い名前を提案する（メソッドの E1108 と同様）。
3. 課題文の宣言を略記ではなく、実際の構文に近い形（ヘッダ 1 行 + `end`）にする。

- 正規形の緩和（`fmt` で直せれば `check` を通す）が、`fmt` が黙って捨てる無効な先頭行（`uses x`）を通していた。E0054 で塞いだ。

- 一般的な「does not match the canonical grammar near X」だけでは、1行ブロックなどの原因が伝わらない。個別の診断が要る。

`bench/run_selfdriven.py v4`。モデルには `ksn check` と `ksn explain` の使い方だけを教え、資料は渡さない。claude-uni は管理設定で Bash を事前許可できないので、
ドライバが check を実行して `--resume` で結果を返す。1 課題あたり最大 5 回書き直し。

結果: 17/20（隠しテストを含む）。書き直しの回数は 0〜4 回が多く、中央は 2 回。

| 課題 | 結果 |
| --- | --- |
| 17 課題 | 合格（0 回: max_of、1 回: fold_squares・bsearch、2 回: 9 課題、3〜4 回: 6 課題） |
| word_count | `check` は通ったが隠しテスト失敗（`not an iterator`: 文字列に対する反復の書き方） |
| stack | `check` は通ったが隠しテスト失敗（`Ok(())` と `true` の取り違え: push の戻り値の型） |
| fact | 6 回目でも E4004（`panics never` の関数で整数 `-`）が残った |

- v3（人手で診断を渡す、20/20）より少し低い。違いは、v4 は 1 課題あたり 5 回までの上限があることと、隠しテストを含めて採点していること。
- 新しく見えたこと: `check` を通っても意味が違うコード（word_count、stack）が出る。型の診断で拾えない種類の誤りで、テスト失敗の文面を返す仕組みが要る。
- fact の E4004 は「`-` を `checked_sub` などに置き換える」直し方が診断から伝わっていない可能性がある。`fix` の候補か説明の追加を検討する。

### v5（v4 の失敗 3 課題を、改善後に再測定）

改善は 2 つ:
- E4004 の診断文を演算子ごとに具体化（`a - b` → `a.checked_sub(b)`〔Option を `match` で処理〕または `wrapping_sub` / `saturating_sub`）。
- ドライバが、`ksn check` を通った後に評価側のテストを実行し、失敗したらその文面をモデルに返す。

結果: fact、word_count、stack が 3 回の書き直しですべて合格（3/3）。v4 の合格 17 課題は再測定していない（同じ条件での 20 本通しは未実施）。

### v6（改善後に 20 課題を通しで再測定）と v7

v6: 19/20（書き直しは 1〜5 回、sum_squares だけ不合格）。同じ条件の v4 は 17/20 だった。
sum_squares が落ちた原因は 2 つ、診断側の問題だった:
- E2020（`u32` を `u64` の変数に入れた）が、変換の仕方を言っていなかった。暗黙の変換も `as` もないので、モデルは直せなかった。
- `ksn explain E2020` が "unknown code" を返した。説明表に無いコードが 11 個あった（E2020 / E2021 / E2030 / E3001 / E3002 / E3003 / E3010 / E3020 / E4010 / E4011 / E4012）。

直したこと: 整数どうしの食い違いに `core.num.<型>.from_<型>(x)`（収まる向き）または `try_from_<型>(x)`（Result）を案内する。説明表に 11 コードを追加（意味はコードが実際に出すメッセージと照合した）。

v7（sum_squares / collatz / fold_squares / parse_u32 だけ再測定）: 4/4、書き直し 2〜3 回。他の課題は再測定していない。

## NIM (nemotron-3.5-lightning-30b-a3b) での E4004 分析

対象: `bench/results/20261112-101144-full-nim-full.json`（ローカル、gitignore 済み）。20 課題、書き直し上限 3、1 回目合格 1/20、最終合格 5/20。

この実行は不完全。20 課題のうち 14 本は API の接続エラーで途中停止している（`Connection refused` 11 本、`Connection reset` 2 本、`Remote end closed` 1 本）。
以下の分析は、1 回目が E4004 で落ちた 5 課題（gcd・fib・is_prime・count_digits・max_of）に限る。

| 課題 | 1 回目の E4004 | 次の試行（モデルの直し方） | 結果 |
| --- | --- | --- | --- |
| fib | `+` (u64) | `a.wrapping_add(b)` | 2 回目で合格 |
| count_digits | `+` 2 箇所 | `count.saturating_add(1u32)`、`i.wrapping_add(1usize)` | 2 回目で合格 |
| max_of | `+` | `i.wrapping_add(1usize)` | 2 回目で合格 |
| gcd | `%` | `x.wrapping_rem(y)` → E1108（`did you mean rem`）→ ヘッダを `panics may` に変えて合格 | 3 回目で合格 |
| is_prime | `*` `%` `+` | 2 回目: `n / i` が E4004、`n.wrapping_rem(i)` が E1108。3 回目: `n.saturating_div(i)` `n.saturating_rem(i)` が E1108 ×2。2 回目は 16000 トークンで出力が切れ、コードなし | 失敗（4 回） |

### 原因の分類

1. 診断の置き換え案が存在しない名前（診断の誤り）。gcd と is_prime の 2 課題。
   - E4004 の `/` `%` の文面は `wrapping_div` / `saturating_div` / `wrapping_rem` / `saturating_rem` を置き換え案として出していた。
   - `spec/stdlib/core/num.sig` では、どの整数型にもこれらは無い。`wrapping_` は `add sub mul neg`（`shl shr` も）、`saturating_` は `add sub mul neg`、`/` と `%` の形は `checked_div` / `checked_rem` だけ。
   - モデルは提案をそのまま書き、E1108 になった（gcd 1 回、is_prime 2 回）。
   - E1108 の近い名前も誤っていた。`did you mean rem` の `rem` は `f32.rem` / `f64.rem` のメソッドで、整数には無い。`did you mean saturating_add` は `saturating_div` と無関係。`nearest_method` が名前の部分一致を先に見るため。
2. 直し方が文面に無い（診断の不足）。
   - `/` `%` の文面は「overflow で panic」と書くだけで、0 で割ると panic することが書かれていない。
   - `panics may` を宣言する選択肢が文面に無い。gcd はモデルが自分で `panics may` にして通したが、is_prime は一度も宣言しなかった。
   - 実行の中で `checked_div` / `checked_rem` を使った試行は 1 つも無かった。Option を `match` で扱う必要があるため、モデルが避けたと見られる（未確認）。
3. 置き換えが正しく、一手で直った例。`+` の wrapping / saturating 置き換え（fib・count_digits・max_of）。E4004 の文面はこの種類では機能している。
4. 出力の上限（診断の外）。is_prime の 2 回目は 16000 トークンで切れた。E4004 が 1 回目に 3 件出たことが長い書き直しにつながったかは未確認。

is_prime は、E4004 の誤った提案に従い、正しい経路（`checked_div` / `checked_rem` の `match`、または `panics may`）を一度も取らなかったことで失敗した。

### 行ったこと（この分析のあとの変更）

- E4004 の文面（`stage0/src/check.rs` の `int_op_may_panic`）: `/` `%` は「division by zero or overflow」と書き、`checked_div` / `checked_rem`（Option、`match`）だけを示し、`wrapping_div` などは存在しないと明記する。全演算子に `panics may` を宣言する選択肢を足す。
- E1108（`check_method_exists`）: `wrapping_div` / `wrapping_rem` / `saturating_div` / `saturating_rem` は、近い名前を出さず、`checked_div(b)` / `checked_rem(b)` を案内する。`did you mean` の形にしないので、`ksn fix` は自動で適用しない。
- `ksn explain E4004` の説明を同じ内容に合わせた。
- テスト: `stage0/tests/cli.rs` 末尾に `e4004_for_div_and_rem_offers_only_the_checked_form` と `e1108_for_wrapping_or_saturating_div_rem_points_to_checked_forms` を追加。
- 検証: `cargo test --release` 全緑（cli 300、他 5）。examples 7 本の `ksn check` は出力なし（変更前と同じ）。`checked_rem` / `checked_div` を `match` で使うコードが `ksn check` を通ることを確認。

チートシートとベンチのプロンプトは変えていない。改善後の効果は、別途ベンチを回して測る（この実行の再測定はしていない）。

### 未対応（読んだだけで確かめていない）

- `method_known` は `wrapping_` などの接頭辞を先に判定し、利用者が定義したメソッド名（例: `wrapping_div`）もすべて E1108 になりうる。
