# 実行速度の計測ハーネス（段階 0）

インタプリタ高速化の前後を比べるための計測。LLM ベンチ（`bench/`）とは別物で、
Kasane プログラムの実行時間だけを測る。

## 構成

| パス | 内容 |
| --- | --- |
| `fib/` `loops/` `vecops/` `hashmap/` `strcat/` `structs/` `closure/` | Kasane の計測パッケージ（ワークロードごとに 1 つ）。`src/<名前>.ksnl` と `kasane.toml` / `kasane.lock` |
| `noop/` | 何もしないパッケージ。起動だけの基準に使う |
| `c/*.c` | 同じ計算をする C 版。`cc -O2` で作る。入力は `KEY=値` の引数で受け取る |
| `run_perf.py` | 計測ハーネス |
| `results/` | 計測結果（JSON と Markdown）と作業コピー。gitignore 済み |

各ワークロードの入力は、Kasane の `const <パッケージ>.N*` と C の引数で同じ値を使う。
期待値 `const <パッケージ>.EXPECT*` は C 版の出力から取る。`ksn run` と
Cranelift の実行ファイルは `check.eq` で期待値を確かめ、外れると終了コード 101 で失敗する。

| パッケージ | 計算 | 既定の入力 | `--quick` の入力 |
| --- | --- | --- | --- |
| `fib` | 再帰 fib（`stack 4096`） | N=27 | N=20 |
| `loops` | 整数ループの総和と素数ふるい（`Vec<bool>`） | N_SUM=1,000,000 / N_SIEVE=200,000 | 100,000 / 20,000 |
| `vecops` | `Vec<u64>` への push、`get` による読み、`v[i] = ..` による書き | N=300,000 | N=30,000 |
| `hashmap` | `HashMap<u32, u32>` の挿入と検索（検索は 2N 回、半分は不在） | N=2,000 | N=200 |
| `strcat` | `String` へ `push_str("ab")` を N 回 | N=200,000 | N=20,000 |
| `structs` | 構造体の `&mut self` 更新と `&self` 読み（メソッド呼び出し） | N=200,000 | N=20,000 |
| `closure` | `F: core.ops.Fn<..>` 境界の関数へ `capture [&k]` のクロージャを渡して N 回呼ぶ | N=300,000 | N=30,000 |
| `noop` | なし（起動のみ） | - | - |

## 使い方

```
cd stage0 && cargo build --release && cd ..
python3 perf/run_perf.py                  # 既定の入力、各 3 回、中央値
python3 perf/run_perf.py --quick          # 小さい入力（動作確認）
python3 perf/run_perf.py --repeat 5 --only fib,loops --tag try
```

- `--ksn <パス>` で ksn を指定できる（既定は `stage0/target/release/ksn`）。
- 結果は `perf/results/perf-<日時>-<入力>[-タグ].json` と `.md` に出る。表は標準出力にも出る。
- ネイティブは LLVM（`ksn build --release`）で作る（Cranelift の `--backend clif` は 2026-11-14 に削除）。生成物 `target/release/<名前>.native` が
  無いとき（`--release` は退避せず E9040 で失敗する。修正プラン 3-2）はその理由を表の下に出す。

## 計測の決まり

- 時間は子プロセスの壁時計時間（`time.perf_counter`）。起動・読み込み・実行をすべて含む。
  インタプリタは `ksn run` のたびに解析と検査もやり直すので、その分が入る。
- 中央値を出す（既定 3 回）。ウォームアップはしない。
- 「起動のみ」の行（noop）が下限になる。ネイティブの数字の大半はこの起動時間。
- 入力は既定の入力を `perf/results/work/` の作業コピーへ書き込んで使う。ソースの定数と既定の入力が
  食い違うと、既定の入力のときは止まる。

## 初回ベースライン (2026-11-12)

既定の入力、各 3 回の中央値、単位 ms。git `d63ba64`、Ubuntu 24.04 / cc 13.3.0 / x86_64。

| ワークロード | 入力 | インタプリタ | Cranelift | C (-O2) | インタプリタ / C | Cranelift / C |

| Vec の push・索引読み・索引書き | N=300,000 | 4801.1 | 5.5 | 2.9 | 1651.0x | 1.9x |

## HashMap の索引化 (2026-11-12)

挿入順は規範なので、反復順は変えていない。検索だけをハッシュで引く（`hkey` の一致で等価を決める従来の規則と同じ）。

- インタプリタ（`value.rs` の `MapV`）: 組の列 `d` はそのまま。`idx: HashMap<hkey, 添字>` を足した。
  削除は `d` の詰め直しに合わせて索引の添字を付け替える（ハッシュは計算し直さない）ので O(n)。
- Cranelift（`clif.rs`）: マップの頭を `{ptr, len, cap}` から `{ptr, len, cap, itab, icap}` (40 バイト) に広げた。
  `itab` は `entry 添字 + 1`（0 = 空き）の開番地法の表。負荷率 3/4 で倍にする。整数・bool・char は
  FNV ではなく黄金比の乗算で、`&str` はバイト列の FNV-1a でハッシュする。削除は組の列を詰めたあと表を作り直す（O(n)）。
  `BtreeMap` は挿入のたびにキー順を保つので索引を使わない（従来どおり線形）。
- 組の列は連続のままなので、`HashMap.iter` の融合ループや `get_mut` の位置（`IdxPlace` / `MapPlace`）は変えていない。

前後の数値（既定の入力 N=2000、各 3 回の中央値、ms。`perf/results/perf-20261112-114503-full-before.md` と `…115402-full-after.md`）:

| ワークロード | 入力 | インタプリタ 前 → 後 | Cranelift 前 → 後 | C (-O2) 前 → 後（揺れ） |
| --- | --- | ---: | ---: | ---: |
| HashMap の挿入・検索（整数キー） | N=2,000 | 818.5 → 88.0 | 13.3 → 6.7 | 1.4 → 4.2 |

入力を 10 倍にした計測（N=20,000。既定の計測と同じ `ksn run` / 生成物の壁時計時間、各 3 回の中央値）:

| ワークロード | 入力 | インタプリタ 前 → 後 | Cranelift 前 → 後 | C (-O2) 前 → 後（揺れ） |
| --- | --- | ---: | ---: | ---: |
| HashMap の挿入・検索（整数キー） | N=20,000 | 115,751.5 → 392.9 | 1,925.6 → 3.9 | 6.4 → 2.5 |

- 10 倍の入力は既定の `--quick` の経路（`WORKLOADS` の quick 入力だけを N=20,000 に替えた一時スクリプト）で測った。
  ハーネス本体の入力表は変えていない。
- 後の Cranelift の数字は起動だけ（4 ms 前後）と同じ程度で、この入力では表の差が計測の揺れに埋もれる。
  N=2,000 の起動だけの値は前後の計測で 1.1 ms と 4.0 ms と揺れたので、Cranelift の比は参考値。
- 検証: `cargo test --release`（回帰テスト `the_hashmap_index_stays_consistent_across_growth_removal_and_reinsertion` を追加）、
  examples 7 本の `ksn test --both`、300 個と 400 個（文字列キー）の自己検査プログラム（増減・削除・再挿入・反復順・`get_mut`）を
  インタプリタとネイティブの両方で通す。定数を 1 つずらすと両方とも失敗することも確かめた。

## 気付いた点

- **【修正済み】`v[i]` の読み取りは長さに比例していた。** 原因は `interp.rs` の `Index` 評価が
  `seq_items` で列全体を `Vec` に複製してから 1 要素を取っていたこと（読み取りごとに O(n)）。
  `value.rs` に `seq_len` / `seq_elem` を足し、要素 1 個だけを複製するようにした（値の意味は変えず、
  コピーか所有かの扱いも同じ）。書き込み `v[i] = x` は元から要素の場所（`IdxPlace`）を使うので対象外。
  前後の数値（同じ入力・`ksn run` の壁時計時間）:
  - 40,000 要素の `if flags[q]` を回す素数ふるい（`sum_to` 1M を含む全体）: 13.9 s → 2.5〜3.0 s。
    同じ程度の `get` 版は 2.9 s。
  - `vecops` の `v[i]` 読み取り版（N=30,000）: 27.9 s → 0.32 s。
  - 既定の入力の `loops` / `vecops`（どちらも `get` で読むので読み取り経路は変わらない）:
    4306.0 → 4000 ms、4851.4 → 4310.8 ms（インタプリタ、中央値。差は計測の揺れの範囲）。
  - 同じ修正で、列の値を比べる `contains` / `copy_from` / 表示など（全件を見るので元から O(n)）は変えていない。
  `loops` と `vecops` は今も `get` で読んでいる（ハーネスの比較用。`v[i]` 版は上の一時コピーで測った）。
- **【修正済み】`HashMap` の検索は線形だった。** 実体は挿入順の組の列で、検索が全件走査だった。
  挿入順の規範（`Kasane 簡易仕様書.md` 8 章・`alloc.collections`）は保ったまま、組の列の上に
  ハッシュの索引表を付けた。詳しくは下の「HashMap の索引化」。
- **ネイティブの数字は起動時間に近い。** 既定の入力では Cranelift が 2〜5 ms で、起動だけの 1.3 ms
  との差が小さい。ネイティブ側の比較には、入力を 10 倍以上にする版が要る。
- **インタプリタの 1 回の操作の重さ。** `structs` は 200,000 回のメソッド呼び出し（`step` と `energy`）で
  2.1 秒、約 10 µs/回。`fib` は約 630,000 回の呼び出しで 1.6 秒、約 2.5 µs/回。
  関数呼び出しとメソッド呼び出しが主な候補。
- **`capture [move k]` のクロージャは `Fn` 境界を満たさない**（E2030）。`capture [&k]` と本体の `*k`
  で通る。`move` の扱いは仕様と合わせて確かめる価値がある。
- Kasane には整数を文字列にする標準の手段が見当たらない（`core.fmt` は規範だけ）。
  そのため計測結果は表示せず、`check.eq` で C 版と一致するかを確かめるだけにした。
  時間は外側（ハーネス）で測る。
