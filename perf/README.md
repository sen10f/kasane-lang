# 実行速度の計測ハーネス（段階 0）

インタプリタ高速化の前後を比べるための計測。LLM ベンチ（`bench/`）とは別物で、
Kasane プログラムの実行時間だけを測る。

## 構成

| パス | 内容 |
| --- | --- |
| `fib/` `loops/` `vecops/` `hashmap/` `strcat/` `structs/` `closure/` | Kasane の計測パッケージ（ワークロードごとに 1 つ）。`src/<名前>.ksnl` と `kasane.toml` / `kasane.lock` |
| `noop/` | 何もしないパッケージ。起動だけの基準に使う |
| `c/*.c` | 同じ計算をする C 版。`cc -O2` で作る。入力は `KEY=値` の引数で受け取る |
| `run_perf.py` | 計測ハーネス |
| `results/` | 計測結果（JSON と Markdown）と作業コピー。gitignore 済み |

各ワークロードの入力は、Kasane の `const <パッケージ>.N*` と C の引数で同じ値を使う。
期待値 `const <パッケージ>.EXPECT*` は C 版の出力から取る。`ksn run` と
Cranelift の実行ファイルは `check.eq` で期待値を確かめ、外れると終了コード 101 で失敗する。

| パッケージ | 計算 | 既定の入力 | `--quick` の入力 |
| --- | --- | --- | --- |
| `fib` | 再帰 fib（`stack 4096`） | N=27 | N=20 |
| `loops` | 整数ループの総和と素数ふるい（`Vec<bool>`） | N_SUM=1,000,000 / N_SIEVE=200,000 | 100,000 / 20,000 |
| `vecops` | `Vec<u64>` への push、`get` による読み、`v[i] = ..` による書き | N=300,000 | N=30,000 |
| `hashmap` | `HashMap<u32, u32>` の挿入と検索（検索は 2N 回、半分は不在） | N=2,000 | N=200 |
| `strcat` | `String` へ `push_str("ab")` を N 回 | N=200,000 | N=20,000 |
| `structs` | 構造体の `&mut self` 更新と `&self` 読み（メソッド呼び出し） | N=200,000 | N=20,000 |
| `closure` | `F: core.ops.Fn<..>` 境界の関数へ `capture [&k]` のクロージャを渡して N 回呼ぶ | N=300,000 | N=30,000 |
| `noop` | なし（起動のみ） | - | - |

## 使い方

```
cd stage0 && cargo build --release && cd ..
python3 perf/run_perf.py                  # 既定の入力、各 3 回、中央値
python3 perf/run_perf.py --quick          # 小さい入力（動作確認）
python3 perf/run_perf.py --repeat 5 --only fib,loops --tag try
```

- `--ksn <パス>` で ksn を指定できる（既定は `stage0/target/release/ksn`）。
- 結果は `perf/results/perf-<日時>-<入力>[-タグ].json` と `.md` に出る。表は標準出力にも出る。
- Cranelift は `ksn build --release --backend clif` で作る。生成物 `target/release/<名前>.native` が
  無いとき（`native backend skipped` など）はその理由を表の下に出し、インタプリタ入りのバンドルは計測しない。

## 計測の決まり

- 時間は子プロセスの壁時計時間（`time.perf_counter`）。起動・読み込み・実行をすべて含む。
  インタプリタは `ksn run` のたびに解析と検査もやり直すので、その分が入る。
- 中央値を出す（既定 3 回）。ウォームアップはしない。
- 「起動のみ」の行（noop）が下限になる。ネイティブの数字の大半はこの起動時間。
- 入力は既定の入力を `perf/results/work/` の作業コピーへ書き込んで使う。ソースの定数と既定の入力が
  食い違うと、既定の入力のときは止まる。

## 初回ベースライン (2026-11-12)

既定の入力、各 3 回の中央値、単位 ms。git `d63ba64`、Ubuntu 24.04 / cc 13.3.0 / x86_64。

| ワークロード | 入力 | インタプリタ | Cranelift | C (-O2) | インタプリタ / C | Cranelift / C |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| **起動のみ（何もしない）** | - | 23.3 | 1.3 | 1.1 | 21.0x | 1.2x |
| 再帰 fib（関数呼び出し） | N=27 | 1603.9 | 2.7 | 1.9 | 858.6x | 1.4x |
| 整数ループ（総和・素数ふるい） | N_SUM=1,000,000, N_SIEVE=200,000 | 4018.7 | 4.0 | 2.1 | 1900.1x | 1.9x |
| Vec の push・索引読み・索引書き | N=300,000 | 4801.1 | 5.5 | 2.9 | 1651.0x | 1.9x |
| HashMap の挿入・検索（整数キー） | N=2,000 | 912.7 | 12.7 | 1.4 | 629.9x | 8.7x |
| 文字列連結（String.push_str） | N=200,000 | 1612.6 | 2.0 | 2.3 | 710.7x | 0.9x |
| 構造体とメソッド呼び出し（&mut self / &self） | N=200,000 | 2118.9 | 1.9 | 1.3 | 1580.1x | 1.4x |
| クロージャ（Fn 境界の関数に渡す） | N=300,000 | 1527.2 | 1.8 | 1.7 | 878.7x | 1.0x |

n/a の項目はなし（全ワークロードで Cranelift の実行ファイルを作れた）。
結果ファイル: `perf/results/perf-20261112-105229-full-baseline.{json,md}`（ローカルのみ）。

## 気付いた点

- **`v[i]` の読み取りはインタプリタで長さに比例する。** 40,000 要素の `if flags[q]`
  を回すと 12.5 秒、同じ処理を `flags.get(q)` にすると 0.3 秒。書き込み `v[i] = x` は速い（同条件で 0.25 秒）。
  最初に作った素数ふるいは二乗のオーダーになり、20,000 で 3 秒、40,000 で 12 秒だった。
  このため `loops` と `vecops` は読み取りを `get` で書いている。段階 1 の最初の候補。
- **`HashMap` の検索は線形。** チートシートにある通り実体は組の列。N=2,000 でも Cranelift（12.7 ms）が
  C（1.4 ms）の 8.7 倍。N を増やすと二乗で伸びる。
- **ネイティブの数字は起動時間に近い。** 既定の入力では Cranelift が 2〜5 ms で、起動だけの 1.3 ms
  との差が小さい。ネイティブ側の比較には、入力を 10 倍以上にする版が要る。
- **インタプリタの 1 回の操作の重さ。** `structs` は 200,000 回のメソッド呼び出し（`step` と `energy`）で
  2.1 秒、約 10 µs/回。`fib` は約 630,000 回の呼び出しで 1.6 秒、約 2.5 µs/回。
  関数呼び出しとメソッド呼び出しが主な候補。
- **`capture [move k]` のクロージャは `Fn` 境界を満たさない**（E2030）。`capture [&k]` と本体の `*k`
  で通る。`move` の扱いは仕様と合わせて確かめる価値がある。
- Kasane には整数を文字列にする標準の手段が見当たらない（`core.fmt` は規範だけ）。
  そのため計測結果は表示せず、`check.eq` で C 版と一致するかを確かめるだけにした。
  時間は外側（ハーネス）で測る。
